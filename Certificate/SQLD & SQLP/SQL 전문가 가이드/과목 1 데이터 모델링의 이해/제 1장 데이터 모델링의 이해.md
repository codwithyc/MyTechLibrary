# 제1절 데이터 모델의 이해

* 데이터 모델링은 **현실 세계의 사람·사물·업무와 관계를 DB에 저장할 수 있는 구조로 표현하는 작업**이다.
* 데이터 모델은 **완성된 설계도**, 데이터 모델링은 **설계도를 만드는 과정**이라고 이해하면 된다.
* 데이터 모델링은 단순히 DB를 만들기 위한 것이 아니라 **업무를 이해·분석·표현하고 DB 설계와 개발에 활용하기 위한 작업**이다.
* 데이터 모델링에서는 **무엇이 있는가 → 엔터티**, **어떤 정보를 가지는가 → 속성**, **서로 어떻게 연결되는가 → 관계**를 파악한다.
* 데이터 모델링에서는 **중복성, 비유연성, 비일관성**을 주의해야 한다.
* 중복성은 **같은 데이터를 여러 곳에 반복해서 저장하는 문제**다.
* 비유연성은 **업무가 조금 바뀌었는데 데이터 모델 전체를 크게 수정해야 하는 문제**다.
* 비일관성은 **같은 의미의 데이터가 서로 다른 값을 가지는 문제**다.

## 데이터 모델링의 3단계

* 데이터 모델링은 **개념적 → 논리적 → 물리적 모델링** 순서로 구체화한다.
* 개념적 데이터 모델링은 **업무에 무엇이 필요한지 큰 그림을 그리는 단계**다.
* 개념적 모델링에서는 주로 **엔터티와 관계를 파악**하며 DBMS나 데이터 타입 같은 구현 내용은 아직 생각하지 않는다.
* 논리적 데이터 모델링은 **엔터티, 속성, 식별자, 관계를 자세히 정의하는 단계**다.
* 논리적 모델링에서는 **PK, FK, 정규화, 관계 구조** 등을 결정한다.
* 물리적 데이터 모델링은 논리 모델을 **Oracle, MySQL 같은 실제 DBMS에 구현할 수 있도록 만드는 단계**다.
* 물리적 모델링에서는 **테이블명, 칼럼명, 데이터 타입, 인덱스, 파티션, 저장 구조, 성능** 등을 결정한다.
* 쉽게 외우면 **개념적 = 큰 그림 / 논리적 = 상세 설계 / 물리적 = 실제 구현**이다.

## 스키마의 3단계 구조

* 스키마는 **데이터베이스의 구조를 바라보는 관점을 나눈 것**이다.
* 외부 스키마는 **사용자마다 필요한 데이터만 바라보는 구조**다.
* 개념 스키마는 **데이터베이스 전체의 논리적인 구조**다.
* 내부 스키마는 **데이터가 실제로 어떻게 저장되는지를 나타내는 물리적인 구조**다.
* 쉽게 외우면 **외부 = 사용자 / 개념 = 전체 DB / 내부 = 실제 저장**이다.

## 데이터 독립성

* 데이터 독립성은 **한 단계의 구조가 바뀌어도 다른 단계에 미치는 영향을 최소화하는 것**이다.
* 논리적 데이터 독립성은 **개념 스키마가 변경되어도 외부 스키마에 미치는 영향을 최소화하는 것**이다.
* 물리적 데이터 독립성은 **내부 스키마가 변경되어도 개념 스키마에 미치는 영향을 최소화하는 것**이다.
* 쉽게 외우면 **논리적 = 외부 ↔ 개념 / 물리적 = 개념 ↔ 내부**다.

# 제2절 엔터티(Entity)

* 엔터티는 **같은 종류의 여러 관리 대상을 모아 놓은 것**이다.
* 쉽게 말하면 **“무엇을 관리할 것인가?”**에 대한 답이다.
* 학생, 고객, 상품, 주문 등이 엔터티가 될 수 있다.
* 인스턴스는 **엔터티에 실제로 존재하는 데이터 한 건**이다.
* `학생`이 엔터티라면 `철수`, `영희`, `민수` 각각은 인스턴스다.
* 속성은 **각 인스턴스를 설명하는 정보**다.
* 엔터티는 업무에서 실제로 필요한 정보여야 한다.
* 엔터티는 각각의 인스턴스를 **식별할 수 있어야 한다.**
* 엔터티는 보통 **2개 이상의 인스턴스**를 가진다.
* 엔터티는 업무 프로세스에서 사용되어야 한다.
* 엔터티는 속성을 가져야 한다.
* 엔터티는 다른 엔터티와 관계를 가지는 것이 일반적이다.

## 엔터티의 분류

* 기본 엔터티는 **업무에 원래 존재하는 기본 대상**이다.
* 기본 엔터티의 예로 고객, 상품, 사원 등이 있다.
* 중심 엔터티는 **핵심 업무가 발생하면서 생기는 중심 대상**이다.
* 중심 엔터티의 예로 주문, 계약, 사고 등이 있다.
* 행위 엔터티는 **업무를 수행하면서 발생하는 상세 기록**이다.
* 행위 엔터티의 예로 주문상세, 결제내역, 계약진행 등이 있다.
* 쉽게 외우면 **기본 = 원래 존재 / 중심 = 핵심 업무 / 행위 = 업무 기록**이다.

# 제3절 속성(Attribute)

* 속성은 **엔터티 안의 인스턴스를 설명하는 정보 항목**이다.
* 쉽게 말하면 **“이 대상에 대해 무엇을 저장할 것인가?”**다.
* 학생 엔터티의 `학생번호`, `이름`, `학년`, `생년월일` 등이 속성이다.
* 속성값은 **속성에 실제로 들어 있는 값**이다.
* 예를 들어 `이름`은 속성이고 `'철수'`는 속성값이다.
* 쉽게 구분하면 **엔터티 = 관리 대상 / 인스턴스 = 실제 한 건 / 속성 = 설명 항목 / 속성값 = 실제 값**이다.
* 속성은 업무에서 실제로 필요한 정보여야 한다.
* 하나의 속성은 **하나의 의미**를 가져야 한다.
* 하나의 인스턴스에서 하나의 속성은 **하나의 값**을 가지는 것이 기본이다.
* 속성값은 정해진 범위 안에서 존재해야 한다.

## 속성의 분류

* 기본 속성은 **업무에서 원래 존재하는 정보**다.
* 기본 속성의 예로 이름, 생년월일, 가격 등이 있다.
* 설계 속성은 **시스템을 설계하면서 관리 목적으로 새로 만든 정보**다.
* 설계 속성의 예로 관리번호, 일련번호 등이 있다.
* 파생 속성은 **다른 속성을 이용해 계산해서 만든 값**이다.
* 파생 속성의 예로 `총금액 = 가격 × 수량`, 생년월일로 계산한 나이 등이 있다.
* 쉽게 외우면 **기본 = 원래 있음 / 설계 = 새로 만듦 / 파생 = 계산함**이다.

## 도메인(Domain)

* 도메인은 **하나의 속성이 가질 수 있는 값의 범위**다.
* 예를 들어 학년 속성에 `1, 2, 3`만 들어갈 수 있다면 이것이 학년의 도메인이다.
* 쉽게 말하면 **도메인 = 이 칼럼에 어떤 값까지 들어올 수 있나?**다.

# 제4절 관계(Relationship)

* 관계는 **두 개 이상의 엔터티가 서로 어떤 관련을 가지는지 나타내는 것**이다.
* 쉽게 말하면 **“누가 누구와 어떻게 연결되어 있는가?”**다.
* `학생 — 수강한다 — 과목`에서 학생과 과목은 엔터티이고 `수강한다`가 관계다.
* 존재 관계는 **존재 자체로 서로 연결되는 관계**다.
* `사원 — 소속된다 — 부서`가 존재 관계의 예다.
* 행위 관계는 **어떤 행동이 발생하면서 만들어지는 관계**다.
* `고객 — 주문한다 — 상품`이 행위 관계의 예다.

## 관계의 차수(Cardinality)

* 관계차수는 **한쪽의 인스턴스 하나가 반대쪽의 몇 개와 연결될 수 있는지를 나타낸다.**
* `1:1`은 **하나와 하나가 연결**되는 관계다.
* `1:M`은 **하나와 여러 개가 연결**되는 관계다.
* `M:N`은 **양쪽 모두 여러 개와 연결**되는 관계다.
* M:N 관계는 실제 DB 설계에서 보통 **중간 엔터티를 만들어 1:M 관계로 풀어낸다.**
* `학생 M : N 과목`은 `학생 1 : M 수강 M : 1 과목`처럼 만들 수 있다.

## 관계의 선택성(Optionality)

* 관계 선택성은 **관계가 반드시 존재해야 하는지, 없어도 되는지를 나타낸다.**
* `○`는 **0, 없어도 됨**을 의미한다.
* `|`는 **1, 반드시 있음**을 의미한다.
* 까치발은 **여러 개(N)**를 의미한다.
* `○|`는 **0 또는 1**을 의미한다.
* `||`는 **정확히 1**을 의미한다.
* `|<`는 **1개 이상**을 의미한다.
* `○<`는 **0개 이상**을 의미한다.
* 관계를 볼 때는 **관계명 + 관계차수 + 관계선택사양**을 확인하면 된다.

# 제5절 식별자(Identifier)

* 식별자는 **엔터티 안에서 각각의 인스턴스를 서로 구별할 수 있게 해주는 속성**이다.
* 쉽게 말하면 **“이 데이터가 정확히 누구인지 알려주는 고유한 이름표”**다.
* 이름이 같은 학생이 여러 명 있어도 학생번호가 다르면 서로 구별할 수 있다.
* 모델의 주식별자는 실제 DB 구현 시 보통 **Primary Key(PK)**와 연결된다.

## 주식별자의 특징

* 주식별자의 특징은 **유일성, 최소성, 불변성, 존재성**이다.
* 유일성은 **같은 식별자 값이 두 개 존재하면 안 된다는 것**이다.
* 최소성은 **인스턴스를 식별하는 데 꼭 필요한 속성만 사용해야 한다는 것**이다.
* 불변성은 **식별자 값이 자주 변경되면 안 된다는 것**이다.
* 존재성은 **식별자 값이 반드시 존재해야 하며 NULL이 될 수 없다는 것**이다.
* 쉽게 외우면 **유·최·불·존 = 유일하게 / 최소로 / 안 바뀌고 / 반드시 존재**다.

## 식별자의 분류

* 대표성에 따라 **주식별자와 보조식별자**로 나눈다.
* 주식별자는 여러 식별자 중 **대표로 선택한 식별자**다.
* 보조식별자는 인스턴스를 구별할 수 있지만 **대표로 선택되지 않은 식별자**다.
* 생성 위치에 따라 **내부식별자와 외부식별자**로 나눈다.
* 내부식별자는 **자기 엔터티에서 스스로 가지는 식별자**다.
* 외부식별자는 **다른 엔터티의 식별자를 가져와 사용하는 것**이며 DB에서는 FK와 연결해서 이해하면 쉽다.
* 속성 개수에 따라 **단일식별자와 복합식별자**로 나눈다.
* 단일식별자는 **속성 하나만으로 인스턴스를 구별**한다.
* 복합식별자는 **두 개 이상의 속성을 합쳐야 인스턴스를 구별**할 수 있다.
* `(주문번호, 상품번호)`로 주문상세를 식별하는 것이 복합식별자의 대표적인 예다.
* 생성 방식에 따라 **본질식별자와 인조식별자**로 나눈다.
* 본질식별자는 **업무적으로 원래 존재하는 의미 있는 식별자**다.
* 인조식별자는 **관리 편의를 위해 시스템에서 새롭게 만든 식별자**다.
* `SEQUENCE`, `AUTO_INCREMENT`, UUID 등을 이용해 만든 ID는 대표적인 인조식별자다.

# 장 요약

* 데이터 모델링 → **현실을 DB 구조로 표현**
* 데이터 모델 → **설계 결과물**
* 개념적 모델링 → **큰 그림**
* 논리적 모델링 → **엔터티·속성·관계·정규화**
* 물리적 모델링 → **DBMS·타입·인덱스·저장 구조**
* 외부 스키마 → **사용자**
* 개념 스키마 → **DB 전체**
* 내부 스키마 → **실제 저장**
* 논리적 독립성 → **외부 ↔ 개념**
* 물리적 독립성 → **개념 ↔ 내부**
* 엔터티 → **무엇을 관리?**
* 인스턴스 → **실제 데이터 한 건**
* 속성 → **무엇을 기록?**
* 속성값 → **실제 들어간 값**
* 도메인 → **허용되는 값의 범위**
* 기본 속성 → **원래 있음**
* 설계 속성 → **새로 만듦**
* 파생 속성 → **계산해서 만듦**
* 관계 → **어떻게 연결?**
* Cardinality → **몇 개와 연결?**
* Optionality → **반드시 연결돼야 하나?**
* 식별자 → **어떻게 구별?**
* 주식별자 → **대표 식별자**
* 유일성 → **중복 X**
* 최소성 → **필요한 것만**
* 불변성 → **변경 최소화**
* 존재성 → **NULL X**
* 내부식별자 → **내 엔터티의 식별자**
* 외부식별자 → **다른 엔터티에서 가져옴**
* 단일식별자 → **속성 하나**
* 복합식별자 → **여러 속성 조합**
* 본질식별자 → **업무에 원래 존재**
* 인조식별자 → **시스템이 새로 생성**
