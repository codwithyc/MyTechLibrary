## 145. Secure SDLC

Secure SDLC(Secure Software Development Life Cycle)는 소프트웨어 개발 생명주기의 각 단계에 **보안 활동을 포함하여 보안 취약점을 사전에 제거하는 개발 방법**입니다.

```text
요구사항
   ↓
설계
   ↓
구현
   ↓
테스트
   ↓
배포 / 운영

각 단계에 보안 활동 적용
```

주요 목적:

* 개발 초기부터 보안 요구사항 반영
* 보안 취약점 사전 제거
* 보안 사고 발생 가능성 감소
* 보안 수정 비용 절감

---

### 1. Seven Touchpoints

Seven Touchpoints는 Gary McGraw가 제안한 **소프트웨어 개발 과정에 보안을 적용하기 위한 7가지 핵심 활동**입니다.

| 활동                          | 설명                      |
| --------------------------- | ----------------------- |
| 코드 검토(Code Review)          | 소스 코드의 보안 취약점 검사        |
| 아키텍처 위험 분석                  | 시스템 설계 단계의 보안 위험 분석     |
| 침투 테스트(Penetration Testing) | 실제 공격과 유사한 방법으로 취약점 검사  |
| 위험 기반 보안 테스트                | 위험도가 높은 기능을 중심으로 보안 테스트 |
| 악용 사례(Abuse Case)           | 공격자의 관점에서 시스템 악용 가능성 분석 |
| 보안 요구사항                     | 개발 초기 단계에서 보안 요구사항 정의   |
| 보안 운영(Security Operations)  | 배포 후 보안 관리 및 대응         |

핵심 흐름:

```text
보안 요구사항
     ↓
악용 사례
     ↓
아키텍처 위험 분석
     ↓
코드 검토
     ↓
위험 기반 테스트
     ↓
침투 테스트
     ↓
보안 운영
```

---

### 2. 보안 3대 요소

정보보안의 3대 요소는 **기밀성, 무결성, 가용성**입니다.

이를 CIA Triad라고 합니다.

```text
C → Confidentiality
I → Integrity
A → Availability
```

#### 기밀성(Confidentiality)

인가된 사용자만 정보에 접근할 수 있도록 하는 것입니다.

예:

* 암호화
* 접근 제어
* 사용자 인증

#### 무결성(Integrity)

정보가 허가 없이 변경되거나 삭제되지 않도록 보장하는 것입니다.

예:

* Hash
* 전자서명
* 접근 권한 관리

#### 가용성(Availability)

인가된 사용자가 필요할 때 정보와 서비스를 사용할 수 있도록 보장하는 것입니다.

예:

* 이중화
* 백업
* 장애 복구
* DDoS 대응

정리:

| 요소  | 핵심               |
| --- | ---------------- |
| 기밀성 | 허가된 사람만 접근       |
| 무결성 | 데이터가 임의로 변경되지 않음 |
| 가용성 | 필요할 때 사용 가능      |

---

## 146. 세션 통제

세션 통제는 사용자가 시스템에 로그인한 이후 생성되는 **세션의 생성, 유지, 종료 등을 안전하게 관리하는 보안 기능**입니다.

주요 보안 방법:

* 안전한 세션 ID 생성
* 세션 ID 암호화
* 일정 시간 후 세션 만료
* 로그아웃 시 세션 삭제
* 중요 작업 시 재인증
* HTTPS 사용

---

### 1. 세션 하이재킹(Session Hijacking)

세션 하이재킹은 공격자가 정상 사용자의 **세션 ID를 탈취하여 해당 사용자인 것처럼 시스템에 접근하는 공격**입니다.

```text
정상 사용자
    ↓ 로그인
Server
    ↓
Session ID 발급
    ↓
공격자가 Session ID 탈취
    ↓
사용자 세션으로 접근
```

공격자는 비밀번호를 알지 못해도 유효한 세션 ID를 확보하면 인증된 사용자처럼 행동할 수 있습니다.

#### 대응 방법

* HTTPS 사용
* 세션 ID를 예측하기 어렵게 생성
* 로그인 후 세션 ID 재발급
* 일정 시간 후 세션 만료
* 로그아웃 시 세션 즉시 삭제
* Cookie에 `HttpOnly`, `Secure` 속성 적용

---

## 147. 입력 데이터 검증 및 표현

사용자가 입력하는 데이터는 항상 신뢰할 수 없기 때문에 **입력값의 형식과 범위를 검증하고 특수 문자를 적절하게 처리해야 합니다.**

---

### 1. SQL 삽입(SQL Injection)

SQL Injection은 사용자 입력값에 악의적인 SQL 문장을 삽입하여 **데이터베이스의 SQL문을 비정상적으로 실행시키는 공격**입니다.

취약한 예:

```java
String sql =
    "SELECT * FROM users WHERE id = '" + id + "'";
```

공격 입력:

```text
' OR '1'='1
```

SQL문:

```sql
SELECT *
FROM users
WHERE id = '' OR '1'='1';
```

조건이 항상 참이 되어 의도하지 않은 데이터가 조회될 수 있습니다.

#### 위험

* 인증 우회
* 개인정보 조회
* 데이터 수정
* 데이터 삭제
* 관리자 권한 획득

#### 대응 방법

가장 중요한 방법은 **Prepared Statement / Parameter Binding**을 사용하는 것입니다.

```java
PreparedStatement pstmt =
    conn.prepareStatement(
        "SELECT * FROM users WHERE id = ?"
    );

pstmt.setString(1, id);
```

추가 대응:

* 입력값 검증
* DB 계정 최소 권한 적용
* 오류 메시지 노출 최소화
* ORM 또는 안전한 Query API 사용

---

### 2. 경로 조작 및 자원 삽입

경로 조작(Path Traversal)은 파일 경로나 URL 등의 입력값을 조작하여 **원래 접근할 수 없는 시스템 파일이나 디렉터리에 접근하는 공격**입니다.

예:

```text
/download?file=test.txt
```

공격:

```text
/download?file=../../../../etc/passwd
```

```text
현재 디렉터리
     ↓
../
     ↓
상위 디렉터리
     ↓
시스템 파일 접근
```

#### 대응 방법

* 사용자 입력값으로 직접 파일 경로 생성 금지
* `../`, `..\` 등의 경로 이동 문자 검증
* 허용된 파일 목록 사용
* 파일 접근 권한 최소화
* 입력값 정규화 후 검증

---

### 3. 크로스사이트 스크립팅(XSS : Cross Site Scripting)

XSS는 웹페이지에 악성 스크립트를 삽입하여 **다른 사용자의 브라우저에서 해당 스크립트를 실행시키는 공격**입니다.

공격 예:

```html
<script>
alert("XSS");
</script>
```

공격 흐름:

```text
공격자
 ↓
악성 Script 입력
 ↓
Web Server
 ↓
다른 사용자가 페이지 조회
 ↓
Browser에서 Script 실행
```

#### 위험

* 세션 쿠키 탈취
* 사용자 정보 탈취
* 악성 사이트 이동
* 화면 변조

#### 주요 유형

| 유형            | 설명                   |
| ------------- | -------------------- |
| Stored XSS    | 악성 스크립트가 서버에 저장      |
| Reflected XSS | 요청값이 그대로 응답에 포함      |
| DOM Based XSS | 브라우저의 DOM 처리 과정에서 발생 |

#### 대응 방법

* 출력값 HTML Encoding
* 사용자 입력값 검증
* `<`, `>`, `"`, `'` 등의 특수 문자 처리
* CSP(Content Security Policy) 적용
* Cookie에 HttpOnly 설정

---

### 4. 운영체제 명령어 삽입

운영체제 명령어 삽입(Command Injection)은 사용자 입력값을 운영체제 명령에 직접 포함하여 **공격자가 임의의 OS 명령을 실행하도록 하는 공격**입니다.

취약한 예:

```text
ping + 사용자 입력
```

정상 입력:

```text
127.0.0.1
```

공격 입력:

```text
127.0.0.1; rm -rf ...
```

```text
Application
     ↓
사용자 입력
     ↓
Shell Command
     ↓
OS에서 명령 실행
```

#### 대응 방법

* 사용자 입력값을 Shell 명령에 직접 연결하지 않음
* Shell 실행 대신 안전한 API 사용
* 허용 목록(Allow List) 방식 검증
* 특수문자 차단
* 애플리케이션 실행 권한 최소화

---

### 5. 메모리 버퍼 오버플로

버퍼 오버플로(Buffer Overflow)는 프로그램이 확보한 메모리 영역보다 **더 많은 데이터를 저장하여 인접한 메모리 영역을 침범하는 취약점**입니다.

```text
정상

Buffer
[ A ][ B ][ C ][ D ]

공격

Buffer
[ A ][ B ][ C ][ D ][ X ][ X ][ X ]
                      ↑
                 영역 초과
```

#### 위험

* 프로그램 비정상 종료
* 메모리 값 변조
* 임의 코드 실행
* 시스템 권한 획득

C언어의 다음 함수는 크기 검증 없이 사용할 경우 위험할 수 있습니다.

```text
strcpy()
strcat()
gets()
```

#### 대응 방법

* 입력 데이터 길이 검증
* 안전한 함수 사용
* Stack Guard 적용
* ASLR(Address Space Layout Randomization)
* DEP / NX 사용

## 148. 보안 기능

### 1. 하드코드된 비밀번호

하드코드된 비밀번호는 소스 코드에 **비밀번호, API Key, 암호화 키 등의 인증 정보를 직접 작성하는 것**입니다.

잘못된 예:

```java
String password = "admin1234";
```

#### 문제점

* 소스 코드 유출 시 비밀번호 노출
* Git 저장소에서 비밀번호 노출 가능
* 비밀번호 변경이 어려움
* 개발자나 관계자가 인증 정보 확인 가능

#### 대응 방법

* 환경 변수 사용
* Secret Manager 사용
* 별도의 보안 설정 저장소 사용
* 비밀번호 암호화 또는 안전한 Hash 처리

예:

```text
Application
    ↓
Environment Variable
또는
Secret Manager
    ↓
Password / API Key
```

## 149. 에러 처리

### 1. 부적절한 예외처리

부적절한 예외처리는 프로그램에서 발생한 오류를 제대로 처리하지 않거나 **내부 시스템 정보를 사용자에게 과도하게 노출하는 문제**입니다.

잘못된 예:

```java
catch (Exception e) {
    e.printStackTrace();
}
```

웹 응답에 Stack Trace가 그대로 노출되면 다음 정보가 유출될 수 있습니다.

* 서버 내부 경로
* 클래스 이름
* DB 정보
* SQL 문
* 프레임워크 버전
* 시스템 구조

#### 대응 방법

* 사용자에게 필요한 오류 메시지만 제공
* 상세 오류는 서버 로그에 기록
* 예외별 적절한 처리 수행
* 빈 `catch` 사용 금지

잘못된 예:

```java
try {
    process();
} catch (Exception e) {
}
```

예외를 무시하면 오류의 원인을 확인하기 어렵고 시스템의 비정상적인 상태를 발견하지 못할 수 있습니다.

## 150. 코드 오류

### 1. 스택 가드(Stack Guard)

Stack Guard는 **스택 버퍼 오버플로 공격을 탐지하기 위한 보안 기법**입니다.

함수의 반환 주소와 지역 변수 사이에 **Canary 값**을 삽입합니다.

```text
Stack

┌──────────────────┐
│ Return Address   │
├──────────────────┤
│ Canary Value     │
├──────────────────┤
│ Local Variable   │
├──────────────────┤
│ Buffer           │
└──────────────────┘
```

버퍼 오버플로가 발생하면 Canary 값이 변경됩니다.

```text
정상
Canary = ABCD

Buffer Overflow
      ↓
Canary = XXXX
      ↓
변조 감지
      ↓
프로그램 종료
```

#### 특징

* Stack Buffer Overflow 탐지
* 함수 반환 주소 변조 방지
* Canary 값을 이용한 무결성 검사

> `Stack Gard`가 아니라 **Stack Guard**입니다.

## 151. 캡슐화

캡슐화(Encapsulation)는 객체의 데이터와 기능을 하나로 묶고 **외부에서 객체 내부의 데이터에 직접 접근하지 못하도록 제한하는 객체지향 개념**입니다.

```text
Class

┌──────────────────┐
│ private data     │
│                  │
│ public method()  │
└──────────────────┘
```

#### 장점

* 데이터 보호
* 정보 은닉
* 유지보수성 향상
* 객체 간 결합도 감소

---

### 1. 접근 지정자(접근 제어자)

접근 지정자는 클래스, 변수, 메소드 등에 **접근할 수 있는 범위를 지정하는 키워드**입니다.

JAVA 기준:

| 접근 제어자      | 같은 클래스 | 같은 패키지 | 상속 관계 | 전체 |
| ----------- | -----: | -----: | ----: | -: |
| `private`   |      O |      X |     X |  X |
| default     |      O |      O |     X |  X |
| `protected` |      O |      O |     O |  X |
| `public`    |      O |      O |     O |  O |

#### private

해당 클래스 내부에서만 접근할 수 있습니다.

```java
private int age;
```

#### default

접근 제어자를 지정하지 않은 경우이며 같은 패키지에서 접근할 수 있습니다.

```java
int age;
```

#### protected

같은 패키지 또는 상속 관계에서 접근할 수 있습니다.

```java
protected int age;
```

#### public

모든 영역에서 접근할 수 있습니다.

```java
public int age;
```

접근 범위:

```text
private
   <
default
   <
protected
   <
public
```

## 152. 암호 알고리즘

암호화는 평문(Plaintext)을 제3자가 알아볼 수 없는 암호문(Ciphertext)으로 변환하는 과정입니다.

```text
Plaintext
   ↓ Encryption
Ciphertext
   ↓ Decryption
Plaintext
```

암호화 방식은 크게 다음과 같이 구분됩니다.

```text
암호화

├─ 대칭키 암호화
│   ├─ DES
│   ├─ AES
│   └─ ARIA
│
└─ 공개키 암호화
    ├─ RSA
    └─ ECC
```

---

### 1. 개인키 암호화(Private Key Encryption) 기법

개인키 암호화는 암호화와 복호화에 **동일한 키를 사용하는 방식**입니다.

대칭키(Symmetric Key) 암호화라고도 합니다.

```text
평문
 ↓
Key A로 암호화
 ↓
암호문
 ↓
Key A로 복호화
 ↓
평문
```

#### 특징

* 암호화와 복호화 속도가 빠름
* 대용량 데이터 암호화에 적합
* 키 관리가 어려움
* 송신자와 수신자가 동일한 비밀키를 공유해야 함

---

### 2. 개인키 암호화 기법의 종류

대칭키 암호 방식은 크게 **블록 암호 방식**과 **스트림 암호 방식**으로 구분합니다.

#### 블록 암호(Block Cipher)

데이터를 일정한 크기의 블록으로 나누어 암호화합니다.

대표 알고리즘:

* DES
* AES
* ARIA
* SEED

```text
Data

[Block 1]
[Block 2]
[Block 3]

각 Block 단위 암호화
```

#### 스트림 암호(Stream Cipher)

데이터를 비트나 바이트 단위로 연속적으로 암호화합니다.

대표 알고리즘:

* RC4
* ChaCha20

```text
Data Stream
 ↓
Bit / Byte 단위 암호화
```

---

### 3. 공개키 암호화(Public Key Encryption) 기법

공개키 암호화는 서로 다른 두 개의 키를 사용하는 **비대칭키(Asymmetric Key) 암호화 방식**입니다.

```text
Public Key
→ 공개 가능

Private Key
→ 소유자만 보관
```

기밀성을 위한 일반적인 흐름:

```text
송신자
 ↓
수신자의 Public Key로 암호화
 ↓
Ciphertext
 ↓
수신자
 ↓
수신자의 Private Key로 복호화
```

#### 특징

* 키 분배가 상대적으로 안전함
* 디지털 서명에 활용 가능
* 대칭키보다 연산 속도가 느림
* 작은 데이터나 키 교환에 주로 사용

대표 알고리즘:

* RSA
* ECC

#### 대칭키와 공개키 비교

| 구분      | 대칭키            | 공개키      |
| ------- | -------------- | -------- |
| 키       | 동일한 키          | 서로 다른 키  |
| 속도      | 빠름             | 느림       |
| 키 관리    | 어려움            | 상대적으로 용이 |
| 대용량 데이터 | 적합             | 비효율적     |
| 대표 알고리즘 | AES, DES, ARIA | RSA, ECC |

---

### 4. ARIA

ARIA는 국내에서 개발된 **대칭키 블록 암호 알고리즘**입니다.

#### 특징

* 대한민국 국가 표준 암호 알고리즘
* 블록 크기: 128bit
* 키 길이: 128 / 192 / 256bit
* AES와 유사한 구조를 가짐
* 공공 및 민간 시스템에서 사용

```text
ARIA

Block : 128bit
Key   : 128 / 192 / 256bit
```

---

### 5. DES

DES(Data Encryption Standard)는 IBM에서 개발되고 미국 표준으로 채택되었던 **대칭키 블록 암호 알고리즘**입니다.

#### 특징

* 블록 크기: 64bit
* 실질적인 암호키 길이: 56bit
* 16 Round 수행
* Feistel 구조 사용

```text
DES

Block : 64bit
Key   : 56bit
Round : 16
```

키 길이가 짧아 Brute Force 공격에 취약하므로 현재는 보안 목적으로 사용하기에 적합하지 않습니다.

이를 개선하기 위해 Triple DES(3DES)가 사용되기도 했습니다.

---

### 6. AES

AES(Advanced Encryption Standard)는 DES의 보안 문제를 해결하기 위해 만들어진 **대칭키 블록 암호 알고리즘**입니다.

현재 널리 사용되는 대표적인 대칭키 암호 방식입니다.

#### 특징

* 블록 크기: 128bit
* 키 길이: 128 / 192 / 256bit
* DES보다 보안성이 높음
* 빠른 암호화 및 복호화

```text
AES

Block : 128bit

AES-128 → Key 128bit
AES-192 → Key 192bit
AES-256 → Key 256bit
```

Round 수:

| 방식      | Round |
| ------- | ----: |
| AES-128 |    10 |
| AES-192 |    12 |
| AES-256 |    14 |

---

### 7. RSA

RSA는 Rivest, Shamir, Adleman이 개발한 대표적인 **공개키 암호 알고리즘**입니다.

큰 정수를 소인수분해하기 어렵다는 수학적 특성을 이용합니다.

```text
Public Key
    ↓
암호화

Ciphertext

Private Key
    ↓
복호화
```

#### 특징

* 공개키와 개인키 사용
* 소인수분해의 어려움을 기반으로 함
* 암호화 및 전자서명에 활용
* 대칭키보다 처리 속도가 느림

주요 활용:

* TLS 인증
* 전자서명
* 키 교환
* 인증서

---

### 8. ECC

ECC(Elliptic Curve Cryptography)는 **타원곡선의 수학적 특성을 이용하는 공개키 암호 방식**입니다.

RSA보다 짧은 키 길이로도 높은 수준의 보안성을 제공하는 것이 특징입니다.

```text
ECC
 ↓
짧은 Key
 +
높은 보안성
```

#### 특징

* 공개키 암호 방식
* 타원곡선 이산 로그 문제 기반
* 키 길이가 상대적으로 짧음
* 연산량과 저장 공간을 줄일 수 있음
* 모바일, IoT 등 자원이 제한된 환경에 적합

#### RSA와 ECC 비교

| 구분    | RSA       | ECC           |
| ----- | --------- | ------------- |
| 기반 문제 | 소인수분해     | 타원곡선 이산 로그    |
| 키 길이  | 상대적으로 김   | 상대적으로 짧음      |
| 연산량   | 큼         | 상대적으로 작음      |
| 활용    | 인증서, 전자서명 | 모바일, IoT, 암호화 |

---

### 암호 알고리즘 핵심 비교

| 알고리즘 | 방식  |  블록 크기 | 키 길이           | 특징           |
| ---- | --- | -----: | -------------- | ------------ |
| DES  | 대칭키 |  64bit | 56bit          | 현재는 취약       |
| AES  | 대칭키 | 128bit | 128/192/256bit | 현재 대표적인 대칭키  |
| ARIA | 대칭키 | 128bit | 128/192/256bit | 국내 표준 암호     |
| RSA  | 공개키 |      - | 가변             | 소인수분해 기반     |
| ECC  | 공개키 |      - | 가변             | 짧은 키로 높은 보안성 |

핵심 암기:

```text
대칭키
→ 빠름
→ 동일한 키
→ DES / AES / ARIA

공개키
→ 느림
→ Public Key + Private Key
→ RSA / ECC
```
