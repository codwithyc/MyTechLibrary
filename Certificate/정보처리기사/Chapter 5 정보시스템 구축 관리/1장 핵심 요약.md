## 126. 소프트웨어 개발 방법론

소프트웨어 개발 방법론은 소프트웨어를 효율적으로 개발하기 위해 **개발 과정, 절차, 방법, 산출물 등을 체계적으로 정리한 방법**입니다.

---

### 1. 구조적 방법론

구조적 방법론(Structured Methodology)은 사용자 요구사항을 파악하여 **처리 중심으로 시스템을 단계적으로 분할하고 구조화하는 방법론**입니다.

복잡한 시스템을 작은 단위로 나누어 분석하고 설계합니다.

#### 특징

* 정형화된 분석 및 설계 절차 사용
* 하향식(Top-Down) 방식
* 기능 중심으로 시스템 분해
* 프로세스와 데이터 흐름을 중심으로 분석
* 모듈화를 통해 복잡성 감소

대표적인 도구:

* 자료 흐름도(DFD)
* 자료 사전(Data Dictionary)
* 소단위 명세서(Mini-Spec)
* 구조도(Structure Chart)

일반적인 개발 절차:

```text
타당성 검토
    ↓
계획
    ↓
요구사항 분석
    ↓
설계
    ↓
구현
    ↓
시험
    ↓
운용 / 유지보수
```

---

### 2. 정보공학 방법론

정보공학 방법론(Information Engineering Methodology)은 기업의 **정보를 중심으로 시스템을 분석하고 설계하는 방법론**입니다.

기업 전체의 업무와 데이터를 통합적으로 분석하여 정보 시스템을 구축합니다.

#### 특징

* 데이터 중심의 개발 방법론
* 기업 전체의 정보 시스템을 체계적으로 구축
* 데이터와 업무 활동을 동시에 고려
* 정보 전략 계획에서 구현까지 전 과정을 지원
* 데이터 모델링을 중요하게 다룸

주요 단계:

```text
정보 전략 계획
      ↓
업무 영역 분석
      ↓
시스템 설계
      ↓
시스템 구축
```

---

### 3. 컴포넌트 기반(CBD) 방법론

CBD(Component Based Development)는 기존에 개발된 **재사용 가능한 컴포넌트를 조립하여 소프트웨어를 개발하는 방법론**입니다.

```text
Component A
      +
Component B
      +
Component C
      ↓
Application
```

#### 특징

* 소프트웨어 재사용성 향상
* 개발 기간 단축
* 개발 비용 절감
* 유지보수성 향상
* 생산성 및 품질 향상

컴포넌트는 독립적으로 개발되고 다른 시스템에서도 재사용할 수 있는 소프트웨어 구성 요소입니다.

---

## 127. S/W 공학의 발전적 추세

### 1. 소프트웨어 재사용의 이점

소프트웨어 재사용(Software Reuse)은 이미 개발되어 검증된 소프트웨어의 전체 또는 일부를 새로운 소프트웨어 개발에 다시 사용하는 것입니다.

#### 이점

* 개발 시간 단축
* 개발 비용 감소
* 개발 생산성 향상
* 소프트웨어 품질 향상
* 프로젝트 실패 위험 감소
* 시스템 구축에 필요한 지식 공유
* 소프트웨어 유지보수성 향상

검증된 코드를 재사용하기 때문에 새로운 코드를 처음부터 개발하는 것보다 오류 발생 가능성도 줄일 수 있습니다.

---

### 2. 소프트웨어 재사용 방법

대표적인 소프트웨어 재사용 방법은 **합성 중심(Composition-Based)**과 **생성 중심(Generation-Based)**입니다.

#### 합성 중심

기존에 만들어진 소프트웨어 부품을 **조립하여 새로운 시스템을 개발**합니다.

```text
Component A
Component B
Component C
     ↓
   조립
     ↓
새로운 시스템
```

블록 구성 방법(Block Construction)이라고도 합니다.

#### 생성 중심

추상화된 명세를 작성하고 이를 기반으로 **프로그램을 자동 또는 반자동으로 생성**합니다.

```text
요구사항 / 명세
      ↓
Generator
      ↓
Program
```

패턴 구성 방법(Pattern Construction)이라고도 합니다.

---

### 3. 소프트웨어 재공학의 주요 활동

소프트웨어 재공학(Software Reengineering)은 기존 소프트웨어를 분석하고 개선하여 **새로운 형태로 재구성하는 활동**입니다.

주요 활동은 다음과 같습니다.

| 활동                       | 설명                            |
| ------------------------ | ----------------------------- |
| 분석(Analysis)             | 기존 소프트웨어의 명세를 확인하고 재공학 대상을 선정 |
| 재구성(Restructuring)       | 기존 기능을 유지하면서 코드나 구조를 개선       |
| 역공학(Reverse Engineering) | 기존 프로그램을 분석하여 설계나 명세를 추출      |
| 이식(Migration)            | 기존 시스템을 새로운 운영 환경으로 이전        |

#### 역공학

```text
소스 코드
   ↓
설계 정보
   ↓
요구사항 / 명세
```

기존 프로그램에서 상위 수준의 정보를 추출합니다.

#### 재공학의 목적

* 유지보수성 향상
* 소프트웨어 수명 연장
* 개발 비용 절감
* 기존 시스템의 품질 개선

---

### 4. CASE 사용의 이점

CASE(Computer Aided Software Engineering)는 소프트웨어 개발 과정의 일부 또는 전체를 **컴퓨터를 이용해 자동화하는 도구**입니다.

#### 이점

* 소프트웨어 개발 기간 단축
* 개발 비용 감소
* 생산성 향상
* 소프트웨어 품질 향상
* 개발 과정 표준화
* 문서 작성 및 관리 용이
* 유지보수성 향상
* 개발자 간 의사소통 향상

---

### 5. CASE의 주요 기능

CASE가 제공하는 주요 기능은 다음과 같습니다.

* 소프트웨어 생명주기 전 단계 연결
* 그래픽 지원
* 모델 작성
* 문서 자동 생성
* 소프트웨어 개발 과정 관리
* 자료 흐름도 작성
* 데이터 모델링
* 코드 자동 생성
* 오류 검사
* 프로젝트 관리

CASE는 지원 범위에 따라 다음과 같이 구분할 수 있습니다.

| 구분      | 지원 영역             |
| ------- | ----------------- |
| 상위 CASE | 요구사항 분석, 설계       |
| 하위 CASE | 구현, 테스트           |
| 통합 CASE | 분석부터 유지보수까지 전체 과정 |

---

### 6. CASE의 원천 기술

CASE 시스템에 사용되는 대표적인 원천 기술에는 다음이 있습니다.

* 구조적 기법
* 프로토타이핑 기술
* 정보 저장소(Repository)
* 분산 처리 기술
* 자동 프로그래밍 기술
* 인공지능 기술
* 그래픽 기술

특히 **Repository**는 CASE에서 개발 과정에 생성되는 각종 정보를 통합적으로 관리하는 저장소입니다.

## 128. 상향식 비용 산정 기법

상향식 비용 산정은 프로젝트를 **작은 작업 단위로 분할한 후 각 작업의 비용을 계산하여 전체 비용을 산정하는 방법**입니다.

```text
작업 A 비용
작업 B 비용
작업 C 비용
    ↓
모두 합산
    ↓
전체 개발 비용
```

대표적인 방법:

* LOC
* 개발 단계별 인월수
* 수학적 산정 기법

---

### 1. LOC 기법

LOC(Line Of Code)는 소프트웨어의 **원시 코드 라인 수를 이용하여 개발 비용을 산정하는 방법**입니다.

예측치는 일반적으로 다음과 같이 계산합니다.

[
예측 LOC =
\frac{낙관치 + 4 \times 기대치 + 비관치}{6}
]

예:

* 낙관치 = 20,000
* 기대치 = 30,000
* 비관치 = 40,000

[
LOC =
\frac{20,000 + (4 \times 30,000) + 40,000}{6}
]

[
= 30,000
]

#### 노력 산정

[
노력(인월) =
\frac{개발기간 \times 투입인원}{}
]

또는 생산성이 주어진 경우:

[
개발 노력 =
\frac{LOC}{1인당 월평균 생산 코드 라인 수}
]

#### 개발 비용

[
개발 비용 =
노력(인월) \times 단위 비용
]

#### 개발 기간

[
개발 기간 =
\frac{노력}{투입 인원}
]

#### 생산성

[
생산성 =
\frac{LOC}{노력(인월)}
]

---

## 129. 수학적 산정 기법

### 1. 수학적 산정 기법의 종류

수학적 산정 기법은 경험적 데이터를 기반으로 만들어진 **수학적 공식을 사용하여 개발 비용을 산정하는 방법**입니다.

대표적인 기법:

| 기법        | 특징                    |
| --------- | --------------------- |
| COCOMO    | LOC 기반 비용 산정          |
| Putnam    | Rayleigh-Norden 곡선 기반 |
| 기능 점수(FP) | 소프트웨어 기능을 기준으로 산정     |

---

### 2. COCOMO 모형 개요

COCOMO(Constructive Cost Model)는 Boehm이 제안한 소프트웨어 비용 산정 모형으로 **개발할 소프트웨어의 규모(LOC)를 기준으로 개발 노력과 기간을 산정**합니다.

기본적인 개발 노력:

[
Effort = a \times (KLOC)^b
]

* Effort: 개발 노력(Man-Month)
* KLOC: 1,000줄 단위의 코드 규모
* a, b: 개발 유형에 따른 상수

COCOMO는 개발 규모와 환경에 따라 프로젝트를 세 가지 유형으로 구분합니다.

---

### 3. COCOMO의 소프트웨어 개발 유형

#### Organic Mode

비교적 작은 규모의 소프트웨어를 개발하는 유형입니다.

특징:

* 소규모 프로젝트
* 경험이 많은 개발자
* 요구사항이 비교적 명확함
* 개발 환경이 안정적

예:

```text
업무용 프로그램
간단한 관리 시스템
```

---

#### Semi-Detached Mode

Organic과 Embedded의 중간 규모에 해당합니다.

특징:

* 중간 규모 프로젝트
* 경험이 다양한 개발자 참여
* 시스템 요구사항의 복잡도가 중간 정도

예:

```text
컴파일러
DBMS
```

---

#### Embedded Mode

하드웨어나 운영 환경 등의 제약이 매우 강한 시스템입니다.

특징:

* 대규모 또는 고도의 복잡성
* 엄격한 성능 요구사항
* 하드웨어와 소프트웨어의 강한 결합
* 높은 신뢰성이 요구됨

예:

```text
항공기 제어 시스템
실시간 제어 시스템
군사용 시스템
```

정리:

| 유형            | 특징            |
| ------------- | ------------- |
| Organic       | 소규모, 단순       |
| Semi-Detached | 중간 규모         |
| Embedded      | 복잡, 제약 조건이 많음 |

---

### 4. Putnam 모형

Putnam 모형은 소프트웨어 개발 과정의 **노력 분포를 Rayleigh-Norden 곡선을 이용하여 표현한 비용 산정 모형**입니다.

시간에 따른 개발 인력의 투입 분포를 나타냅니다.

```text
투입 인원
   │
   │          /\
   │        /    \
   │      /        \
   │____/____________\_____ 시간
```

#### 특징

* 소프트웨어 생명주기 전체의 노력 분포를 고려
* 개발 기간과 투입 인력의 관계를 수학적으로 표현
* 대규모 프로젝트의 비용 산정에 활용
* 개발 기간이 짧아지면 필요한 인력이 크게 증가할 수 있음

Putnam 모형을 기반으로 개발된 자동화 도구가 **SLIM**입니다.

---

### 5. 기능 점수(FP) 모형 - 가중치 중대 요인

기능 점수(Function Point)는 소프트웨어의 코드 길이가 아니라 **사용자에게 제공되는 기능의 수와 복잡도를 기준으로 규모를 산정하는 방법**입니다.

기능 점수를 계산할 때 대표적으로 평가하는 기능 요소는 다음과 같습니다.

| 기능 요소            | 설명                  |
| ---------------- | ------------------- |
| 외부 입력(EI)        | 시스템 외부에서 들어오는 입력    |
| 외부 출력(EO)        | 시스템에서 외부로 제공되는 출력   |
| 외부 조회(EQ)        | 입력에 따라 데이터를 조회하여 제공 |
| 내부 논리 파일(ILF)    | 시스템 내부에서 관리되는 데이터   |
| 외부 인터페이스 파일(EIF) | 다른 시스템에서 관리되는 데이터   |

각 기능에 대해 복잡도에 따라 **낮음, 보통, 높음** 등의 가중치를 부여합니다.

기능 점수에 영향을 주는 주요 요인으로는 다음과 같은 것들이 있습니다.

* 자료 통신
* 분산 처리
* 성능
* 운영 환경
* 온라인 데이터 입력
* 사용 편의성
* 온라인 갱신
* 복잡한 처리
* 재사용성
* 설치 용이성
* 변경 용이성

#### 특징

* 프로그래밍 언어에 영향을 적게 받음
* 개발 초기 단계에서 산정 가능
* 사용자 관점에서 기능 규모를 측정

---

### 6. 자동화 추정 도구 - SLIM

SLIM(Software Life Cycle Management)은 **Putnam 모형을 기반으로 개발 비용과 일정을 자동으로 산정하는 도구**입니다.

주요 기능:

* 개발 비용 산정
* 개발 기간 예측
* 투입 인력 예측
* 프로젝트 일정 분석

```text
Putnam Model
     ↓
   SLIM
```

> 시험에서는 **Putnam → SLIM**의 관계를 함께 기억하는 것이 중요합니다.

## 130. 프로젝트 일정 계획

프로젝트 일정 계획은 프로젝트를 일정 기간 내에 완료하기 위해 **작업 순서, 기간, 자원 등을 계획하고 관리하는 활동**입니다.

대표적인 일정 계획 기법:

* PERT
* CPM
* 간트 차트

---

### 1. PERT(프로그램 평가 및 검토 기술)

PERT(Program Evaluation and Review Technique)는 프로젝트의 작업별 소요 시간을 **확률적으로 계산하여 전체 일정을 계획하는 기법**입니다.

작업 시간이 불확실한 프로젝트에 적합합니다.

PERT에서는 세 가지 시간을 사용합니다.

| 시간       | 의미            |
| -------- | ------------- |
| 낙관 시간(O) | 가장 빠르게 완료될 경우 |
| 기대 시간(M) | 일반적으로 예상되는 시간 |
| 비관 시간(P) | 가장 늦게 완료될 경우  |

기대 시간은 다음과 같이 계산합니다.

[
기대시간 =
\frac{O + 4M + P}{6}
]

예:

* 낙관 시간 = 2일
* 기대 시간 = 5일
* 비관 시간 = 8일

[
\frac{2 + (4 \times 5) + 8}{6}
==============================

5일
]

#### 특징

* 작업 시간이 불확실한 경우 사용
* 프로젝트 일정 예측
* 작업 간 선후 관계 파악
* 임계 경로 파악 가능

---

### 2. CPM(임계 경로 기법)

CPM(Critical Path Method)은 프로젝트를 완료하는 데 필요한 작업들의 관계를 분석하여 **전체 프로젝트의 최소 완료 시간을 결정하는 기법**입니다.

여러 경로 중 작업 시간이 가장 긴 경로를 **임계 경로(Critical Path)**라고 합니다.

예:

```text
         B(3)
       ↗      ↘
A(2)            D(4)
       ↘      ↗
         C(5)
```

경로 1:

```text
A → B → D
2 + 3 + 4 = 9
```

경로 2:

```text
A → C → D
2 + 5 + 4 = 11
```

따라서 임계 경로:

```text
A → C → D
```

프로젝트 최소 완료 기간:

```text
11일
```

---

### 3. 임계 경로 소요 기일

임계 경로의 소요 기간은 **임계 경로에 포함된 모든 작업의 소요 시간을 더하여 계산**합니다.

[
임계경로 소요기간 =
각 작업의 소요시간 합계
]

예:

```text
A(3) → B(4) → C(5)
```

이라면:

[
3 + 4 + 5 = 12일
]

임계 경로에 포함된 작업이 지연되면 **전체 프로젝트 일정도 지연**됩니다.

또한 임계 경로에 속한 작업의 여유 시간(Slack Time)은 일반적으로 `0`입니다.

---

### 4. 간트 차트(Gantt Chart)

간트 차트는 프로젝트의 작업 일정과 진행 상태를 **막대 형태로 표현하는 일정 관리 도구**입니다.

예:

```text
          1주  2주  3주  4주  5주

요구분석   ████
설계           ████████
구현                 ████████████
테스트                         ████████
```

#### 특징

* 작업 시작 및 종료 시점 확인
* 작업 기간 확인
* 진행 상황 파악이 쉬움
* 작업별 일정 비교 가능

#### 단점

* 작업 간의 정확한 의존 관계를 표현하기 어려움
* 프로젝트 규모가 커지면 복잡해질 수 있음

---

## 131. 소프트웨어 개발 방법론 결정

### 1. 프로젝트 관리

프로젝트 관리는 제한된 자원과 기간을 이용하여 프로젝트의 목표를 달성할 수 있도록 **계획하고 통제하는 활동**입니다.

주요 관리 대상:

```text
프로젝트 관리

├─ 일정 관리
├─ 비용 관리
├─ 품질 관리
├─ 인력 관리
├─ 위험 관리
├─ 의사소통 관리
└─ 범위 관리
```

대표적인 프로젝트 관리 요소:

| 요소 | 설명                 |
| -- | ------------------ |
| 범위 | 프로젝트가 수행해야 하는 작업   |
| 일정 | 프로젝트 완료 기간         |
| 비용 | 프로젝트에 필요한 비용       |
| 품질 | 산출물이 충족해야 하는 품질 수준 |
| 자원 | 인력, 장비 등의 관리       |
| 위험 | 프로젝트에 영향을 줄 위험 요소  |

---

### 2. 위험 관리

위험 관리(Risk Management)는 프로젝트 수행 중 발생할 수 있는 위험 요소를 **사전에 식별하고 분석하여 대응하는 활동**입니다.

일반적인 위험 관리 과정:

```text
위험 식별
   ↓
위험 분석
   ↓
위험 평가
   ↓
대응 계획
   ↓
위험 감시 및 통제
```

#### 위험 대응 전략

| 전략             | 설명                   |
| -------------- | -------------------- |
| 회피(Avoidance)  | 위험 원인을 제거            |
| 완화(Mitigation) | 위험 발생 가능성이나 영향을 감소   |
| 전가(Transfer)   | 위험을 다른 조직이나 제3자에게 이전 |
| 수용(Acceptance) | 위험을 받아들이고 발생 시 대응    |

위험 분석 시 일반적으로 다음 요소를 고려합니다.

[
위험 노출도 =
위험 발생 확률 \times 위험 발생 시 손실
]

---

## 132. 소프트웨어 개발 표준

### 1. ISO/IEC 12207

ISO/IEC 12207은 **소프트웨어 생명주기 프로세스를 정의한 국제 표준**입니다.

소프트웨어의 개발부터 운영, 유지보수까지 전체 생명주기에서 수행해야 할 프로세스를 정의합니다.

대표적인 프로세스 범주는 다음과 같습니다.

#### 기본 생명주기 프로세스

* 획득
* 공급
* 개발
* 운영
* 유지보수

#### 지원 생명주기 프로세스

* 문서화
* 형상 관리
* 품질 보증
* 검증
* 확인
* 공동 검토
* 감사
* 문제 해결

#### 조직 생명주기 프로세스

* 관리
* 기반 구조
* 개선
* 교육

---

### 2. CMMI의 개념

CMMI(Capability Maturity Model Integration)는 조직의 **소프트웨어 개발 및 관리 프로세스의 성숙도를 평가하고 개선하기 위한 모델**입니다.

목적:

* 개발 프로세스 개선
* 소프트웨어 품질 향상
* 프로젝트 관리 능력 향상
* 조직의 개발 역량 평가

CMMI의 성숙도는 총 **5단계**로 구분합니다.

---

### 3. CMMI의 소프트웨어 프로세스 성숙도 5단계

| 단계 | 명칭                             | 설명                       |
| -- | ------------------------------ | ------------------------ |
| 1  | 초기(Initial)                    | 프로세스가 비정형적이고 개인 역량에 의존   |
| 2  | 관리(Managed)                    | 프로젝트 단위로 기본적인 관리 프로세스 구축 |
| 3  | 정의(Defined)                    | 조직 차원의 표준 프로세스를 정의       |
| 4  | 정량적 관리(Quantitatively Managed) | 프로세스를 측정하고 정량적으로 관리      |
| 5  | 최적화(Optimizing)                | 지속적으로 프로세스를 개선           |

흐름:

```text
1. Initial
      ↓
2. Managed
      ↓
3. Defined
      ↓
4. Quantitatively Managed
      ↓
5. Optimizing
```

#### 핵심 암기

```text
초 → 관 → 정 → 정량 → 최
```

---

### 4. SPICE(소프트웨어 처리 개선 및 능력 평가 기준)

SPICE(Software Process Improvement and Capability Determination)는 소프트웨어 프로세스를 평가하고 개선하기 위한 **국제 프로세스 평가 모델**입니다.

ISO/IEC 15504로 표준화되었으며, 프로세스의 수행 능력을 단계별로 평가합니다.

목적:

* 소프트웨어 프로세스 개선
* 개발 조직의 프로세스 능력 평가
* 프로세스 위험 파악
* 공급 업체의 개발 능력 평가

---

### 5. SPICE의 프로세스 수행 능력 단계

SPICE의 프로세스 수행 능력은 **0~5단계**로 구분합니다.

| 단계      | 명칭              | 설명                       |
| ------- | --------------- | ------------------------ |
| Level 0 | 불완전(Incomplete) | 프로세스가 구현되지 않았거나 목적 달성 실패 |
| Level 1 | 수행(Performed)   | 프로세스가 수행되고 목적을 달성        |
| Level 2 | 관리(Managed)     | 프로세스를 계획하고 관리            |
| Level 3 | 확립(Established) | 표준 프로세스를 정의하고 적용         |
| Level 4 | 예측(Predictable) | 측정 자료를 이용하여 정량적으로 관리     |
| Level 5 | 최적화(Optimizing) | 지속적으로 프로세스를 개선           |

흐름:

```text
0. 불완전
   ↓
1. 수행
   ↓
2. 관리
   ↓
3. 확립
   ↓
4. 예측
   ↓
5. 최적화
```

> CMMI는 **1~5단계**, SPICE는 **0~5단계**라는 차이를 기억하면 좋습니다.

---

## 133. 소프트웨어 개발 방법론 테일러링

### 1. 소프트웨어 개발 방법론 테일러링의 개요

테일러링(Tailoring)은 조직에서 사용하는 표준 소프트웨어 개발 방법론을 **프로젝트의 특성과 환경에 맞게 수정하여 적용하는 활동**입니다.

모든 프로젝트에 동일한 개발 방법론을 그대로 적용하면 불필요한 절차가 발생할 수 있기 때문에 프로젝트 규모와 특성을 고려하여 적절하게 조정합니다.

```text
표준 개발 방법론
       ↓
프로젝트 특성 분석
       ↓
불필요한 절차 제거 / 필요한 절차 추가
       ↓
프로젝트 맞춤 방법론
```

#### 목적

* 프로젝트 특성에 맞는 개발 절차 적용
* 불필요한 작업 제거
* 개발 생산성 향상
* 프로젝트 품질 향상
* 개발 비용 및 일정 최적화

---

### 2. 소프트웨어 개발 방법론 테일러링 고려사항

테일러링 시 고려사항은 크게 **내부적 기준**과 **외부적 기준**으로 구분할 수 있습니다.

#### 내부적 기준

프로젝트 자체의 특성과 관련된 요소입니다.

| 기준      | 설명                 |
| ------- | ------------------ |
| 목표 환경   | 개발 시스템의 운영 환경      |
| 요구사항    | 프로젝트의 기능 및 품질 요구사항 |
| 프로젝트 규모 | 개발 규모와 복잡도         |
| 보유 기술   | 개발 조직이 보유한 기술      |
| 구성원 능력  | 참여 개발자의 경험과 역량     |

#### 외부적 기준

법률이나 표준처럼 외부 환경에 의해 영향을 받는 요소입니다.

| 기준       | 설명                 |
| -------- | ------------------ |
| 법적 제약사항  | 관련 법률 및 규정         |
| 표준 품질 기준 | 준수해야 하는 산업 및 품질 표준 |

정리:

```text
테일러링 고려사항

내부
├─ 목표 환경
├─ 요구사항
├─ 프로젝트 규모
├─ 보유 기술
└─ 구성원 능력

외부
├─ 법적 제약사항
└─ 표준 품질 기준
```

## 134. 소프트웨어 개발 프레임워크

### 1. 소프트웨어 개발 프레임워크

소프트웨어 개발 프레임워크(Framework)는 소프트웨어 개발에 필요한 **공통 기능과 구조를 미리 제공하여 개발자가 핵심 비즈니스 로직에 집중할 수 있도록 하는 기반 환경**입니다.

프레임워크에는 일반적으로 다음 요소가 포함됩니다.

* 공통 라이브러리
* 개발 규칙
* 기본 아키텍처
* 공통 컴포넌트
* 개발 도구
* 인터페이스

대표적인 프레임워크:

```text
Java
→ Spring Framework

Python
→ Django
→ Flask

JavaScript / TypeScript
→ NestJS
→ Angular
```

#### 라이브러리와 프레임워크 차이

라이브러리는 개발자가 필요한 기능을 **직접 호출**하지만 프레임워크는 프레임워크가 전체 실행 흐름을 제어하고 개발자가 작성한 코드를 호출합니다.

```text
Library

내 코드
  ↓ 호출
Library


Framework

Framework
   ↓ 호출
내 코드
```

이를 **제어의 역전(IoC, Inversion of Control)**이라고 합니다.

---

### 2. 프레임워크의 특성

소프트웨어 프레임워크의 대표적인 특성은 다음과 같습니다.

#### 모듈화(Modularity)

프레임워크는 기능을 모듈 단위로 분리하여 제공합니다.

* 변경에 따른 영향을 최소화
* 유지보수 용이
* 기능 재사용 가능

---

#### 재사용성(Reusability)

공통 기능을 여러 프로젝트에서 반복해서 사용할 수 있습니다.

```text
인증
로깅
DB 연결
예외 처리
```

등의 공통 기능을 다시 개발할 필요가 없습니다.

---

#### 확장성(Extensibility)

기존 구조를 크게 변경하지 않고 새로운 기능을 확장할 수 있습니다.

```text
기존 Framework
      +
새로운 Component
      ↓
기능 확장
```

---

#### 제어의 역흐름(Inversion of Control)

일반적인 프로그램에서는 개발자가 프로그램의 실행 흐름을 제어하지만, 프레임워크에서는 **프레임워크가 전체 흐름을 제어하고 필요한 시점에 개발자의 코드를 호출**합니다.

```text
일반 프로그램

내 코드 → Library 호출


Framework

Framework → 내 코드 호출
```

이를 **IoC(Inversion of Control)**라고 합니다.

---

프레임워크의 핵심 특성을 정리하면 다음과 같습니다.

| 특성      | 설명                 |
| ------- | ------------------ |
| 모듈화     | 기능을 독립적인 모듈로 구성    |
| 재사용성    | 공통 기능을 반복적으로 활용    |
| 확장성     | 기존 구조를 유지하면서 기능 확장 |
| 제어의 역흐름 | 프레임워크가 실행 흐름을 제어   |
