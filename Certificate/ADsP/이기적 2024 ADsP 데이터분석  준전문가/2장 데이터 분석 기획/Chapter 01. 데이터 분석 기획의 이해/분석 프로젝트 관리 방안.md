# 분석 프로젝트 관리 방안

분석 프로젝트 관리 방안은 데이터 분석 프로젝트를 수행할 때 발생할 수 있는 **범위, 일정, 품질, 위험, 자원, 의사소통 문제를 체계적으로 관리하는 방법**이다.

일반적인 시스템 개발 프로젝트는 요구사항이 비교적 명확한 경우가 많다.

```markdown
회원가입 기능을 만든다.
결제 API를 만든다.
관리자 페이지를 만든다.
```

하지만 분석 프로젝트는 시작 시점에 결과가 명확하지 않은 경우가 많다.

```markdown
이 데이터로 고객 이탈을 예측할 수 있을까?
매출 감소 원인을 데이터로 설명할 수 있을까?
어떤 변수가 결과에 가장 큰 영향을 주는가?
분석 결과가 실제 업무 개선으로 이어질 수 있을까?
```

즉, 분석 프로젝트는 **데이터 품질, 모델 성능, 분석 결과 활용 가능성**에 따라 프로젝트 방향이 계속 바뀔 수 있다.

```markdown
분석 프로젝트 관리 = 불확실성이 큰 분석 과제를 일정, 품질, 위험, 자원 관점에서 체계적으로 관리하는 것
```

네가 정리해둔 빅데이터 파트처럼 개념을 먼저 설명하고 표로 압축하는 방식이 시험 직전 복습에 좋다.

# 01. 분석 과제 관리 영역

분석 과제 관리 영역은 분석 프로젝트를 관리할 때 특히 주의해야 하는 핵심 요소다.

ADsP에서는 보통 다음 4가지를 중심으로 이해하면 된다.

```markdown
데이터 크기
데이터 복잡도
속도
분석 복잡도
```

| 관리 영역   | 핵심 의미                       |
| ------- | --------------------------- |
| 데이터 크기  | 분석해야 할 데이터의 양이 얼마나 큰가       |
| 데이터 복잡도 | 데이터의 구조와 형태가 얼마나 복잡한가       |
| 속도      | 데이터를 얼마나 빠르게 수집·처리·분석해야 하는가 |
| 분석 복잡도  | 분석 기법과 모델링 과정이 얼마나 복잡한가     |

이 4가지는 분석 프로젝트의 난이도와 관리 방식에 직접적인 영향을 준다.

---

## 1) 데이터 크기, Data Size

### 데이터 크기의 개념

**데이터 크기**는 분석에 사용되는 데이터의 양을 의미한다.

데이터 크기가 커질수록 저장, 처리, 분석, 전송에 필요한 비용과 시간이 증가한다.

예를 들어 다음과 같은 경우 데이터 크기가 큰 프로젝트라고 볼 수 있다.

```markdown
수년간의 고객 거래 데이터 분석
대량의 로그 데이터 분석
수백만 명의 사용자 행동 데이터 분석
IoT 센서에서 실시간으로 수집되는 대규모 데이터 분석
```

데이터 크기가 크면 단순히 분석 시간이 길어지는 것만 문제가 아니다.
데이터 저장 구조, 처리 인프라, 샘플링 전략, 분산 처리 방식까지 함께 고려해야 한다.

---

### 데이터 크기가 프로젝트에 미치는 영향

| 영향       | 설명                               |
| -------- | -------------------------------- |
| 저장 공간 증가 | 대량 데이터를 저장할 인프라가 필요하다            |
| 처리 시간 증가 | 데이터 정제, 변환, 분석 시간이 길어진다          |
| 비용 증가    | 저장소, 서버, 클라우드 비용이 증가할 수 있다       |
| 성능 저하    | 대용량 데이터 처리 시 시스템 성능 문제가 발생할 수 있다 |
| 샘플링 필요   | 전체 데이터를 모두 분석하기 어려우면 표본 추출이 필요하다 |

시험에서는 이렇게 이해하면 된다.

```markdown
데이터 크기 = 데이터 양이 커질수록 저장·처리·분석 비용과 시간이 증가하는 관리 영역
```

---

### 데이터 크기 관리 방안

| 관리 방안      | 설명                          |
| ---------- | --------------------------- |
| 데이터 범위 정의  | 분석에 필요한 기간, 대상, 항목을 명확히 정한다 |
| 샘플링 활용     | 전체 데이터가 너무 크면 대표 표본을 추출한다   |
| 분산 처리 검토   | 대용량 데이터는 분산 저장·분산 처리를 고려한다  |
| 저장 구조 최적화  | 데이터 저장 방식과 조회 방식을 효율화한다     |
| 불필요 데이터 제거 | 분석 목적과 무관한 데이터는 제외한다        |

데이터가 많다고 항상 좋은 것은 아니다.
분석 목적과 관련 없는 데이터가 많으면 오히려 비용만 증가하고 분석 품질은 낮아질 수 있다.

```markdown
시험 포인트: 데이터 크기는 저장·처리 비용, 성능, 샘플링, 인프라와 관련된다.
```

---

## 2) 데이터 복잡도, Data Complexity

### 데이터 복잡도의 개념

**데이터 복잡도**는 데이터의 구조, 형태, 출처, 품질이 얼마나 복잡한지를 의미한다.

데이터 크기가 “얼마나 많은가”의 문제라면,
데이터 복잡도는 “얼마나 다루기 어려운가”의 문제다.

예를 들어 다음과 같은 경우 데이터 복잡도가 높다.

```markdown
정형 데이터와 비정형 데이터를 함께 분석해야 하는 경우
여러 시스템의 데이터를 통합해야 하는 경우
데이터 형식이 서로 다른 경우
결측치, 이상치, 중복 데이터가 많은 경우
텍스트, 이미지, 음성, 로그 데이터가 포함된 경우
```

---

### 데이터 복잡도가 프로젝트에 미치는 영향

| 영향         | 설명                          |
| ---------- | --------------------------- |
| 데이터 통합 어려움 | 여러 출처의 데이터를 하나로 결합하기 어렵다    |
| 전처리 부담 증가  | 결측치, 이상치, 중복 처리 작업이 많아진다    |
| 품질 관리 필요   | 데이터 오류가 분석 결과에 직접적인 영향을 준다  |
| 해석 어려움     | 비정형 데이터나 복합 데이터는 의미 해석이 어렵다 |
| 분석 기간 증가   | 데이터 이해와 정제에 많은 시간이 소요된다     |

분석 프로젝트에서 실제로 가장 많은 시간이 걸리는 부분은 모델링보다 데이터 준비와 전처리인 경우가 많다.

시험에서는 이렇게 이해하면 된다.

```markdown
데이터 복잡도 = 데이터 구조, 형식, 출처, 품질이 복잡하여 통합·정제·해석이 어려운 정도
```

---

### 데이터 복잡도 관리 방안

| 관리 방안     | 설명                           |
| --------- | ---------------------------- |
| 데이터 구조 파악 | 데이터의 형식, 컬럼, 관계, 의미를 먼저 이해한다 |
| 데이터 품질 점검 | 결측치, 이상치, 중복, 오류를 확인한다       |
| 데이터 표준화   | 서로 다른 형식과 기준을 통일한다           |
| 메타데이터 관리  | 데이터 정의, 출처, 의미, 생성 기준을 문서화한다 |
| 전처리 기준 수립 | 정제, 변환, 통합 기준을 명확히 정한다       |

데이터 복잡도는 분석 품질에 직접적인 영향을 준다.
데이터 의미를 잘못 이해하면 분석 결과도 잘못 해석될 수 있다.

```markdown
시험 포인트: 데이터 복잡도는 데이터 통합, 전처리, 품질, 표준화와 관련된다.
```

## 3) 속도, Speed

### 속도의 개념

**속도**는 데이터를 얼마나 빠르게 수집, 처리, 분석, 제공해야 하는지를 의미한다.

빅데이터 환경에서는 데이터가 빠르게 생성되고,
분석 결과도 빠르게 제공되어야 하는 경우가 많다.

예를 들어 다음과 같은 경우 속도가 중요한 프로젝트다.

```markdown
실시간 이상 거래 탐지
실시간 추천 시스템
실시간 로그 모니터링
실시간 재고 관리
실시간 광고 입찰 분석
```

속도가 중요한 프로젝트에서는 단순히 정확한 분석만으로는 부족하다.
분석 결과가 늦게 나오면 실제 의사결정에 활용할 수 없기 때문이다.

---

### 속도가 프로젝트에 미치는 영향

| 영향         | 설명                        |
| ---------- | ------------------------- |
| 실시간 처리 필요  | 데이터를 즉시 수집하고 처리해야 한다      |
| 빠른 의사결정 요구 | 분석 결과가 지연되면 가치가 떨어진다      |
| 시스템 성능 중요  | 처리 지연, 병목, 장애를 관리해야 한다    |
| 운영 안정성 필요  | 실시간 시스템은 장애 발생 시 영향이 크다   |
| 자동화 필요     | 사람이 직접 처리하기 어려워 자동화가 필요하다 |

예를 들어 이상 거래 탐지는 거래가 끝난 뒤 며칠 후에 결과가 나오면 의미가 줄어든다.
이런 분석은 빠르게 탐지하고 즉시 대응할 수 있어야 한다.

시험에서는 이렇게 이해하면 된다.

```markdown
속도 = 데이터 발생부터 분석 결과 제공까지 요구되는 처리 속도와 실시간성
```

---

### 속도 관리 방안

| 관리 방안        | 설명                                 |
| ------------ | ---------------------------------- |
| 실시간 처리 구조 검토 | 스트리밍 처리, 이벤트 기반 처리 등을 고려한다         |
| 처리 병목 파악     | 데이터 수집, 저장, 분석 과정의 지연 지점을 찾는다      |
| 자동화 적용       | 반복 처리와 분석 결과 제공 과정을 자동화한다          |
| 성능 모니터링      | 처리 시간, 응답 시간, 장애 여부를 지속적으로 확인한다    |
| 우선순위 설정      | 모든 데이터를 실시간 처리하지 않고 중요한 데이터부터 처리한다 |

모든 분석이 실시간일 필요는 없다.
따라서 분석 기획 단계에서 **실시간 처리가 필요한지, 배치 처리로 충분한지**를 구분해야 한다.

```markdown
시험 포인트: 속도는 실시간 처리, 빠른 의사결정, 자동화, 성능 관리와 관련된다.
```

## 4) 분석 복잡도, Analytic Complexity

### 분석 복잡도의 개념

**분석 복잡도**는 분석 기법, 모델링 과정, 변수 관계, 알고리즘 적용이 얼마나 복잡한지를 의미한다.

데이터가 단순하더라도 분석 목적이 복잡하면 분석 복잡도는 높아질 수 있다.

예를 들어 다음과 같은 경우 분석 복잡도가 높다.

```markdown
여러 변수가 복합적으로 결과에 영향을 주는 경우
예측 모델의 정확도와 해석 가능성을 함께 고려해야 하는 경우
다양한 분석 기법을 비교해야 하는 경우
모델 성능 개선을 위해 반복 실험이 필요한 경우
분석 결과를 현업이 이해할 수 있게 설명해야 하는 경우
```

---

### 분석 복잡도가 프로젝트에 미치는 영향

| 영향        | 설명                        |
| --------- | ------------------------- |
| 모델 선택 어려움 | 어떤 분석 기법이 적합한지 판단해야 한다    |
| 반복 실험 증가  | 변수 선택, 모델 튜닝, 검증을 반복해야 한다 |
| 해석 어려움    | 복잡한 모델은 결과 설명이 어려울 수 있다   |
| 전문 인력 필요  | 통계, 머신러닝, 도메인 지식이 필요하다    |
| 검증 부담 증가  | 모델 성능과 안정성을 충분히 검토해야 한다   |

분석 복잡도가 높다고 무조건 좋은 분석은 아니다.
시험에서는 “복잡한 모델보다 목적에 맞고 해석 가능한 모델이 중요하다”는 관점으로 이해하면 좋다.

```markdown
분석 복잡도 = 분석 기법과 모델링 과정이 복잡하여 선택, 검증, 해석이 어려운 정도
```

---

### 분석 복잡도 관리 방안

| 관리 방안       | 설명                          |
| ----------- | --------------------------- |
| 분석 목표 명확화   | 해결하려는 문제와 성공 기준을 먼저 정한다     |
| 단순 모델부터 시작  | 복잡한 모델보다 기본 모델로 기준 성능을 확인한다 |
| 모델 검증 체계 수립 | 학습, 검증, 테스트 데이터를 구분해 평가한다   |
| 해석 가능성 고려   | 현업이 이해하고 활용할 수 있는 결과를 제공한다  |
| 반복 실험 관리    | 실험 조건, 변수, 결과를 기록하고 비교한다    |

분석 프로젝트에서는 모델 성능만큼이나 결과 해석과 활용 가능성도 중요하다.

```markdown
시험 포인트: 분석 복잡도는 모델 선택, 반복 실험, 검증, 해석 가능성과 관련된다.
```

# 분석 과제 관리 영역 비교

| 관리 영역   | 핵심 질문              | 주요 관리 포인트            |
| ------- | ------------------ | -------------------- |
| 데이터 크기  | 데이터 양이 얼마나 큰가?     | 저장, 처리 비용, 샘플링, 인프라  |
| 데이터 복잡도 | 데이터가 얼마나 다루기 어려운가? | 통합, 정제, 품질, 표준화      |
| 속도      | 얼마나 빠르게 처리해야 하는가?  | 실시간성, 자동화, 성능, 병목    |
| 분석 복잡도  | 분석 방법이 얼마나 복잡한가?   | 모델 선택, 검증, 해석, 반복 실험 |

암기 방식은 다음과 같다.

```markdown
크기 = 양
복잡도 = 구조와 품질
속도 = 실시간성
분석 복잡도 = 모델과 해석 난이도
```

# 02. 주제별 프로젝트 관리 체계, 방안

주제별 프로젝트 관리 체계는 분석 프로젝트를 성공적으로 수행하기 위해 관리해야 할 영역을 구분한 것이다.

분석 프로젝트는 데이터, 모델, 시스템, 조직이 함께 움직이기 때문에 단순히 일정만 관리해서는 부족하다.

보통 다음과 같은 관리 영역을 함께 고려한다.

```markdown
범위 관리
일정 관리
품질 관리
위험 관리
의사소통 관리
자원 관리
변경 관리
성과 관리
```

---

## 1) 범위 관리

### 범위 관리의 개념

**범위 관리**는 분석 프로젝트에서 무엇을 할지, 무엇은 하지 않을지를 명확히 정하는 것이다.

분석 프로젝트는 진행 중에 새로운 질문이 계속 생길 수 있다.

```markdown
이 변수도 분석해보자.
이 데이터도 추가해보자.
모델을 하나 더 만들어보자.
대시보드 기능도 추가하자.
```

이런 요구가 계속 늘어나면 프로젝트 범위가 커지고 일정이 지연될 수 있다.

| 구분     | 설명                            |
| ------ | ----------------------------- |
| 목적     | 분석 대상과 수행 범위를 명확히 정의          |
| 주요 활동  | 분석 목표 정의, 포함/제외 범위 설정, 산출물 정의 |
| 관리 포인트 | 범위 확대 방지, 요구사항 변경 관리          |

시험에서는 이렇게 이해하면 된다.

```markdown
범위 관리 = 분석 프로젝트에서 할 일과 하지 않을 일을 명확히 정하는 것
```

---

## 2) 일정 관리

### 일정 관리의 개념

**일정 관리**는 분석 프로젝트의 각 단계를 언제까지 수행할지 계획하고 관리하는 것이다.

분석 프로젝트는 데이터 확보나 전처리에서 예상보다 많은 시간이 걸릴 수 있다.

| 구분     | 설명                         |
| ------ | -------------------------- |
| 목적     | 프로젝트를 정해진 기간 안에 완료         |
| 주요 활동  | 단계별 일정 수립, 마일스톤 설정, 지연 관리  |
| 관리 포인트 | 데이터 준비 일정, 반복 실험 일정, 검증 일정 |

시험에서는 이렇게 이해하면 된다.

```markdown
일정 관리 = 분석 단계별 수행 기간과 마일스톤을 관리하는 것
```

---

## 3) 품질 관리

### 품질 관리의 개념

**품질 관리**는 분석 결과가 신뢰할 수 있고 활용 가능한 수준인지 관리하는 것이다.

분석 프로젝트의 품질은 단순히 모델 정확도만으로 결정되지 않는다.

```markdown
데이터 품질이 적절한가?
분석 절차가 타당한가?
모델 성능이 충분한가?
결과 해석이 올바른가?
업무 활용이 가능한가?
```

| 구분     | 설명                         |
| ------ | -------------------------- |
| 목적     | 신뢰할 수 있는 분석 결과 확보          |
| 주요 활동  | 데이터 품질 점검, 모델 성능 평가, 결과 검증 |
| 관리 포인트 | 정확성, 재현성, 해석 가능성, 활용 가능성   |

시험에서는 이렇게 이해하면 된다.

```markdown
품질 관리 = 데이터, 모델, 결과의 신뢰성과 활용 가능성을 관리하는 것
```

---

## 4) 위험 관리

### 위험 관리의 개념

**위험 관리**는 분석 프로젝트 수행 중 발생할 수 있는 문제를 미리 파악하고 대응하는 것이다.

분석 프로젝트에서는 다음과 같은 위험이 자주 발생한다.

```markdown
필요한 데이터가 없다.
데이터 품질이 낮다.
모델 성능이 기대보다 낮다.
현업이 분석 결과를 활용하지 않는다.
개인정보나 보안 이슈가 발생한다.
일정과 비용이 초과된다.
```

| 구분     | 설명                          |
| ------ | --------------------------- |
| 목적     | 프로젝트 실패 가능성 감소              |
| 주요 활동  | 위험 식별, 영향도 평가, 대응 방안 수립     |
| 관리 포인트 | 데이터 위험, 기술 위험, 조직 위험, 보안 위험 |

시험에서는 이렇게 이해하면 된다.

```markdown
위험 관리 = 분석 프로젝트의 실패 요인을 사전에 식별하고 대응하는 것
```

---

## 5) 의사소통 관리

### 의사소통 관리의 개념

**의사소통 관리**는 프로젝트 참여자 간에 필요한 정보를 정확하게 공유하는 것이다.

분석 프로젝트는 현업, 분석가, IT 담당자, 의사결정자가 함께 참여하기 때문에 의사소통이 매우 중요하다.

| 구분     | 설명                         |
| ------ | -------------------------- |
| 목적     | 이해관계자 간 정보 공유와 협업 강화       |
| 주요 활동  | 회의, 보고, 이슈 공유, 결과 설명       |
| 관리 포인트 | 현업 요구사항, 분석 결과 해석, 의사결정 지원 |

시험에서는 이렇게 이해하면 된다.

```markdown
의사소통 관리 = 현업, 분석가, IT 담당자 간 분석 목적과 결과를 일치시키는 것
```

---

## 6) 자원 관리

### 자원 관리의 개념

**자원 관리**는 분석 프로젝트에 필요한 인력, 예산, 도구, 인프라를 관리하는 것이다.

분석 프로젝트에는 분석가만 필요한 것이 아니다.

```markdown
데이터를 제공하는 현업 담당자
데이터 수집과 저장을 지원하는 IT 담당자
모델링을 수행하는 분석가
결과를 활용하는 의사결정자
```

| 구분     | 설명                          |
| ------ | --------------------------- |
| 목적     | 프로젝트 수행에 필요한 자원 확보          |
| 주요 활동  | 인력 배정, 예산 관리, 분석 도구와 인프라 확보 |
| 관리 포인트 | 전문 인력, 분석 환경, 데이터 접근 권한     |

시험에서는 이렇게 이해하면 된다.

```markdown
자원 관리 = 분석 수행에 필요한 인력, 예산, 도구, 인프라를 확보하고 관리하는 것
```

## 7) 변경 관리

### 변경 관리의 개념

**변경 관리**는 프로젝트 진행 중 발생하는 요구사항, 데이터, 분석 방법, 일정 변경을 통제하는 것이다.

분석 프로젝트는 진행하면서 새로운 사실을 발견하는 경우가 많다.
그래서 변경 자체를 막을 수는 없지만, 변경을 관리하지 않으면 프로젝트가 흔들릴 수 있다.

| 구분     | 설명                          |
| ------ | --------------------------- |
| 목적     | 변경으로 인한 혼란과 일정 지연 방지        |
| 주요 활동  | 변경 요청 검토, 영향도 분석, 승인 절차 운영  |
| 관리 포인트 | 범위 변경, 데이터 변경, 모델 변경, 일정 변경 |

시험에서는 이렇게 이해하면 된다.

```markdown
변경 관리 = 분석 프로젝트 중 발생하는 변경 사항을 통제하고 반영하는 것
```

## 8) 성과 관리

### 성과 관리의 개념

**성과 관리**는 분석 프로젝트가 실제로 목표한 효과를 만들었는지 평가하는 것이다.

분석 프로젝트의 성과는 모델 성능뿐 아니라 비즈니스 효과로도 평가해야 한다.

| 구분     | 설명                            |
| ------ | ----------------------------- |
| 목적     | 분석 프로젝트의 효과 확인                |
| 주요 활동  | 성과 지표 정의, 분석 성과 측정, 개선 사항 도출  |
| 관리 포인트 | 모델 성능, 비용 절감, 매출 증가, 업무 효율 향상 |

시험에서는 이렇게 이해하면 된다.

```markdown
성과 관리 = 분석 결과가 실제 비즈니스 가치로 이어졌는지 평가하는 것
```

# 주제별 프로젝트 관리 체계 정리

| 관리 체계   | 핵심 질문                 | 주요 관리 내용               |
| ------- | --------------------- | ---------------------- |
| 범위 관리   | 어디까지 분석할 것인가?         | 분석 대상, 산출물, 제외 범위 정의   |
| 일정 관리   | 언제까지 수행할 것인가?         | 단계별 일정, 마일스톤, 지연 관리    |
| 품질 관리   | 결과를 신뢰할 수 있는가?        | 데이터 품질, 모델 성능, 결과 검증   |
| 위험 관리   | 실패 요인은 무엇인가?          | 데이터, 기술, 조직, 보안 위험 대응  |
| 의사소통 관리 | 이해관계자가 같은 방향을 보고 있는가? | 회의, 보고, 요구사항, 결과 공유    |
| 자원 관리   | 필요한 자원이 있는가?          | 인력, 예산, 도구, 인프라 확보     |
| 변경 관리   | 변경을 어떻게 통제할 것인가?      | 변경 요청, 영향 분석, 승인 절차    |
| 성과 관리   | 실제 효과가 있었는가?          | 모델 성능, 업무 성과, 개선 효과 측정 |

암기 방식은 다음과 같다.

```markdown
범위 = 어디까지
일정 = 언제까지
품질 = 믿을 수 있는가
위험 = 실패 요인은 무엇인가
의사소통 = 같은 방향을 보고 있는가
자원 = 필요한 것이 있는가
변경 = 바뀐 것을 어떻게 통제할 것인가
성과 = 실제 효과가 있었는가
```

# 시험 직전 암기 문장

```markdown
분석 프로젝트 관리는 불확실성이 큰 분석 과제를
범위, 일정, 품질, 위험, 자원, 의사소통, 변경, 성과 관점에서 체계적으로 관리하는 것이다.

분석 과제 관리 영역은 데이터 크기, 데이터 복잡도, 속도, 분석 복잡도로 구분된다.

데이터 크기는 분석해야 할 데이터의 양을 의미하며,
데이터 양이 커질수록 저장, 처리, 분석 비용과 시간이 증가한다.

데이터 복잡도는 데이터의 구조, 형식, 출처, 품질이 복잡한 정도를 의미하며,
복잡도가 높을수록 데이터 통합, 정제, 표준화, 품질 관리가 중요하다.

속도는 데이터를 얼마나 빠르게 수집, 처리, 분석, 제공해야 하는지를 의미하며,
실시간 처리, 자동화, 시스템 성능 관리와 관련된다.

분석 복잡도는 분석 기법과 모델링 과정의 복잡한 정도를 의미하며,
모델 선택, 반복 실험, 성능 검증, 해석 가능성 관리가 중요하다.

주제별 프로젝트 관리 체계에는 범위 관리, 일정 관리, 품질 관리, 위험 관리,
의사소통 관리, 자원 관리, 변경 관리, 성과 관리가 포함된다.

범위 관리는 분석 대상과 산출물의 범위를 정하는 것이고,
일정 관리는 단계별 수행 기간과 마일스톤을 관리하는 것이다.

품질 관리는 데이터, 모델, 분석 결과의 신뢰성을 관리하는 것이고,
위험 관리는 프로젝트 실패 요인을 사전에 식별하고 대응하는 것이다.

의사소통 관리는 이해관계자 간 정보를 공유하는 것이며,
자원 관리는 분석 수행에 필요한 인력, 예산, 도구, 인프라를 확보하는 것이다.

변경 관리는 프로젝트 중 발생하는 요구사항, 데이터, 분석 방법의 변경을 통제하는 것이고,
성과 관리는 분석 결과가 실제 비즈니스 가치로 이어졌는지 평가하는 것이다.
```
