# CHAPTER 03 네트워크의 이해

## 문제 1번 : 정답 3

```
"다음 중 OSI 7 계층의 상위 계층부터 하위 계층 순으로 사용하는 전송 단위를 바르게 나열한 것은?"

1. 비트-프레임-패킷-세그먼트-메시지
2. 비트-프레임-세그먼트-패킷-메시지
3. 메시지-세그먼트-패킷-프레임-비트
4. 메시지-패킷-세그먼트-프레임-비트
```

우리가 보통 **하위 계층 -> 상위 계층**로 외우면 `비트 -> 프레임 -> 패킷 -> 세그먼트 -> 메시지` 인데 문제는 **상위 계층부터 하위 계층 순서**를 물어봤으니깐 반대로 뒤집으면 됩니다.

그래서 정답은 3번입니다.  

그리고 OSI 7계층하고 연결하면 이렇게 됩니다.
```
| 계층           | 전송 단위 |
| ------------ | ----- |
| 7~5계층        | 메시지   |
| 4계층 전송 계층    | 세그먼트  |
| 3계층 네트워크 계층  | 패킷    |
| 2계층 데이터링크 계층 | 프레임   |
| 1계층 물리 계층    | 비트    |
```

## 문제 2번 : 정답 3

```
"다음 중 리눅스 시스템에 설정된 게이트웨이의 주소 값을 확인하는 명령으로 틀린 것은?"

1. ip
2. route
3. arp
4. netstat
```

이 문제는 결국 **"게이트웨이는 어떤 정보에 들어 있느냐"**를 물어보는 문제입니다. 게이트워이는 다른 네트워크로 나갈 때 거치는 **라우터 주소**라서, 보통 **라우팅 테이블**에서 확인합니다.

```
내 PC
  ↓
같은 네트워크가 아니네?
  ↓
게이트웨이로 보냄
  ↓
다른 네트워크 / 인터넷
```

그래서 게이트웨이는 이런 명령들과 연결 됩니다.

| 명령            | 무엇을 확인?             | 게이트웨이 확인 |
| ------------- | ------------------- | -------- |
| `ip route`    | 라우팅 테이블             | O        |
| `route -n`    | 라우팅 테이블             | O        |
| `netstat -rn` | 라우팅 테이블             | O        |
| `arp`         | IP 주소와 MAC 주소 대응 관계 | **X**    |

예를 들어 `ip route`를 치면 이런 식으로 나오게 됩니다.

```
default via 192.168.0.1 dev eth0
```

여기서

```
default via 192.168.0.1
            ↑
         게이트웨이
```

즉 `192.168.0.1`이 기본 게이트웨이입니다.  
`route -n`도 비슷하게 
```
Destination   Gateway
0.0.0.0       192.168.0.1
```
처럼 게이트웨이를 보여줄 수 있습니다.

`neststat -rn`도 라우팅 테이블을 봅여주니까 역시 가능합니다.  
반면 `arp`는 완전히 다른 걸 보게 됩니다.

`arp -n`은 대략 `192.168.0.1 -> aa:bb:cc:dd:ee:ff` 처럼 "이 IP 주소는 어떤 MAC 주소를 쓰고 있지?"를 확인하는 명령입니다.

즉
```
route / ip route / netstat -r
→ 어디로 보낼까?
→ 게이트웨이/라우팅 정보

arp
→ 이 IP의 MAC 주소가 뭐지?
```
이 차이입니다.

## 문제 3번 : 정답 4

```
"다음 설명과 같을 때 설정하는 서브넷마스크 값으로 가장 알맞은 것은?"

C 클래스에 속한 1개의 네트워크를 할당받은 상태이다.
이 네트워크 대역을 사용하는 부서가 8곳이라
8개의 서브넷을 구성하려고 한다.

1. 255.255.255.8
2. 255.255.255.64
3. 255.255.255.192
4. 255.255.255.224
```

이 문제는 다음과 같은 형식으로 풀어나가면 됩니다.  
C 클래스의 기본 서브넷 마스크는 `255.255.255.0` 이고, 마지막 `0` 부분에서 **서브넷을 몇 개로 나눌지 결정**하는 것입니다.

현재 필요한 서브넷은 8개니깐 `2^? = 8` 를 찾으면 됩니다. `2^3=8` 즉 3비트를 서브넷용으로 가져오면 된다는 뜻입니다.  
`00000000` 인데 앞에 3비트를 서브넷용으로 바꾸면 `11100000` 이 됩니다. 

이거 십진수로 변경하면
```
1   1   1   0   0   0   0   0
128 64  32  16  8   4   2   1

128 + 64 + 32 = 224
```
이 됩니다.

그래서 `255.255.255.224`가 되는 겁니다.

## 문제 4번 : 정답 3

```
"다음 설명에 해당하는 네트워크 관련 파일로 알맞은 것은?"

시스템 전체에 네트워크 연결 허용 여부, 호스트명,
기본 게이트웨이 주소를 설정하기 위한 파일이다.

1. /etc/hosts
2. /etc/resolv.conf
3. /etc/sysconfig/network
4. /etc/sysconfig/network-scripts
```

이 문제는 **"리눅스에서 네트워크 설정 파일들이 각각 무엇을 담당하는지"** 구분하는 문제입니다.  
문제에서 나온 핵심 단어는 3가지 입니다.
- 시스템 전체 네트워크 사용 여부
- 호스트명
- 기본 게이트웨이

이 세 가지를 예전 Red Hat 계열 리눅스에서 시스템 전체 기준으로 설정하던 파일이 `/etc/sysconfig/network` 입니다.  
예전에는 대략 다음과 같은 내용이 들어갈 수 있었습니다.
```
NETWORKING=yes
HOSTNAME=server.example.com
GATEWAY=192.168.0.1
```

각각 풀면
```
NETWORKING=yes
→ 네트워크 기능을 사용할 것인가?

HOSTNAME=server.example.com
→ 이 컴퓨터의 이름은 무엇인가?

GATEWAY=192.168.0.1
→ 다른 네트워크로 나갈 때 어느 게이트웨이를 사용할 것인가?
```

그래서 문제 설명하고 정확히 연결됩니다.

### 다른 보기들은 무엇인가?
| 파일                               | 역할                           |
| -------------------------------- | ---------------------------- |
| `/etc/hosts`                     | 호스트 이름과 IP 주소를 직접 연결         |
| `/etc/resolv.conf`               | DNS 서버 설정                    |
| `/etc/sysconfig/network`         | **시스템 전체 네트워크 설정**           |
| `/etc/sysconfig/network-scripts` | 각 네트워크 인터페이스 설정 파일들이 있던 디렉터리 |

### 1. `/etc/hots`는 이런 식입니다.
```
127.0.0.1   localhost
192.168.0.10 server1
```

즉 **"이 이름은 이 IP 주소야."**를 직접 적는 파일입니다.  
DNS를 거치지 않고 로컬에서 이름과 IP를 연결할 때 사용합니다.

### 2. `/etc/resolv.conf`는 DNS 설정 파일입니다.
```
nameserver 8.8.8.8
nameserver 1.1.1.1
```

즉 **"도메인 이름을 IP로 바꿀 때 어느 DNS 서버한테 물어볼까?"**를 설정하는 파일입니다.

### 4. `/etc/sysconfig/network-scripts`는 파일 하나가 아니라 디렉터리입니다.

예전 Red Hat/CentOS에서는 안에
```
/etc/sysconfig/network-scripts/
    ├── ifcfg-eth0
    ├── ifcfg-eth1
    └── ...
```

처럼 네트워크 카드별 설정 파일을 넣었습니다.

예를 들어 `eth0`에
```
IPADDR=192.168.0.10
NETMASK=255.255.255.0
```

그래서 구분하면 
```
/etc/sysconfig/network
→ 컴퓨터 전체 네트워크 설정

/etc/sysconfig/network-scripts/
→ 각각의 네트워크 카드 설정
```

## 문제 5번 : 정답 1

```
"다음 설명에 해당하는 관련 기구로 알맞은 것은?"

이기종 시스템 간 상호 통신을 위하여 컴퓨터
네트워크 프로토콜 디자인과 통신 계층으로 나눠
설명한 네트워크 참조 모델이다.

1. ISO
2. EIA
3. IEEE
4. ICANN
```

이 문장의 핵심 문장은 **"이기종 시스템 간 상호 통신을 위하여 ... 통신 계층으로 나눠 설명한 네트워크 참조 모델"**  
이 부분입니다. 

이건 바로 **OSI 7계층 모델**을 설명하고 있습니다.
```
OSI = Open Systems Interconnection

7 응용 계층
6 표현 계층
5 세션 계층
4 전송 계층
3 네트워크 계층
2 데이터링크 계층
1 물리 계층
```

그리고 이 **OSI 참조 모델을 만든 국제 표준화 기구가 ISO**입니다.

```
ISO
↓
OSI 참조 모델 제정
↓
서로 다른 컴퓨터/시스템끼리
통신할 수 있도록 통신 과정을 7계층으로 구분
```

여기서 **이기종 시스템**이라는 말도 알아두면 좋습니다.  

예를 들면
```
Windows PC
Linux 서버
Cisco 네트워크 장비
다른 제조사의 컴퓨터
```

이런 서로 다른 장비들이 제각각 자기 방식만 쓰면 통신하기 어려우니 **"통신 과정을 이런 계층으로 나눠서 표준화하자."**라고 만든게  
OSI 모델이라고 보면 됩니다.

| 기구      | 주로 하는 일                            |
| ------- | ---------------------------------- |
| **ISO** | 국제 표준 제정, **OSI 7계층**              |
| EIA     | 전자·통신 장비 관련 표준                     |
| IEEE    | LAN, Ethernet, Wi-Fi 같은 네트워크 기술 표준 |
| ICANN   | 인터넷 도메인 이름과 IP 주소 체계 관리            |


## 문제 6번 : 정답 4

```
"다음 (    ) 안에 들어갈 내용으로 알맞은 것은?"

B 클래스 주소 대역 하나를 할당받아 서브넷 마스크를
255.255.192.0으로 설정하였다.

이 경우 생성되는 서브네트워크의 개수는 (ㄱ)이다.

또한 인터넷 연결이 가능한 구성을 기준으로 할 때,
하나의 서브네트워크당 사용 가능한 IP 주소 수는 (ㄴ)이다.

1. ㄱ : 2, ㄴ : 2^16 - 2
2. ㄱ : 2, ㄴ : 2^16 - 3
3. ㄱ : 4, ㄴ : 2^14 - 2
4. ㄱ : 4, ㄴ : 2^14 - 3
```

### 먼저 B 클래스의 기본값부터 본다.
B 클래스의 기본 서브넷 마스크는 `255.255.0.0` 2진수로 바꾸면 `11111111.11111111.00000000.00000000` 앞의 `1`이 16개니깐 `/16` 입니다.

### 문제에서 준 서브넷 마스크를 2지수로 바꾼다
문제 `255.255.192.0` 여기서 `192 = 11000000` 이니깐 전체는  
`11111111.11111111.11000000.00000000` `1`이 총 18개니깐 `/18` 입니다.

### 왜 서브넷이 4개인가?
기본 B 클래스는 `/16`이었는데 문제에서는 `/18`을 사용했습니다.
```
기본 : /16
문제 : /18

18 - 16 = 2비트
```

즉 원래 호스트용이던 비트 중 **2비트를 서브넷 구분용으로 가져온 것**입니다. 

```
원래
네트워크 16비트 | 호스트 16비트

변경 후
네트워크 16비트 | 서브넷 2비트 | 호스트 14비트
```

서브넷 비트가 2개면 가능한 조합은 
```
00
01
10
11
```

총 4개 즉 `2^2 = 4` 따라서 4개의 서브넷

### 왜 호스트 비트가 14개인가?

IPv4 주소는 전체가 32비트입니다.  
현재 `/18` 이니 앞의 18비트를 네트워크 + 서브넷 구분에 사용하고 있습니다.  
그래서 남는 비트는 `32-18 = 14비트` 이 14비트로 한 서브넷 안의 IP 주소를 만들어 `2^14 = 16,384개` 입니다.

### 그런데 왜 `2^14 -3`인가?
일반적인 서브넷 문제라면 두 주소를 사용할 수 없습니다.
```
네트워크 주소      -1
브로드캐스트 주소   -1
```

그래서 일반적으로는 `2^14 - 2`가 사용 가능한 호스트 주소 수입니다.  
그런데 이 문제에서는 **"인터넷 연결이 가느한 구성을 기준으로"** 이라고 조건을 붙였습니다.  
시험의 출제 기준에서는 인터넷 연결에 사용할 **게이트웨이 IP 1개**도 따로 잡는 것으로 계산한 것입니다..

```
전체 IP             2^14
네트워크 주소         -1
브로드캐스트 주소      -1
게이트웨이 주소        -1
────────────────────────
사용 가능한 IP       2^14 - 3
```

## 문제 9번 : 정답 1

```
"다음 중 설정된 IP 주소를 확인하는 명령으로 알맞은 것은?"

1. ip addr show
2. ip show addr
3. ip show
4. ip list
```

이 문제는 `ip` 명령어의 **문법 순서**를 아는지 보는 문제입니다.  
기본 형태는 이렇게 생각하면 됩니다.

```
ip [대상] [동작]
```

여기서 IP 주소를 보고 싶으면 대상이 `addr(address)`이고, 보여달라는 동작이 `show`입니다.  
`ip addr show`는 자연어로 읽으면 **ip 주소(addr)를 보여줘(show)라는** 뜻입니다.

실제로 실행하면 대략 이런 식으로 나옵니다.

```
2: eth0:
    inet 192.168.0.10/24
```

여기서 `192.168.0.10`이 현재 설정된 IPv4 주소입니다.

## 문제 10번 : 정답 3

```
"다음 중 OSI 7 LAYER의 애플리케이션 계층과 거리가 먼 것은?"

1. HTTP
2. FTP
3. TCP

```

## 문제 12번 : 정답 2

```
"route 명령의 실행 결과가 다음과 같을 때
169.254.0.0/16 대역의 라우팅 테이블을 삭제하려고 한다.
(    ) 안에 들어갈 내용으로 알맞은 것은?"

[ihd@www ~]$ route -n

Kernel IP routing table

Destination     Gateway         Genmask         Flags
192.168.159.0   0.0.0.0         255.255.255.0   U
169.254.0.0     0.0.0.0         255.255.0.0     U
0.0.0.0         192.168.159.2   0.0.0.0         UG

[ihd@www ~]$ cat << __EOF__ >> /etc/sysconfig/network
> (    )
> __EOF__

1. NOZEROCONF=no
2. NOZEROCONF=yes
3. ZEROCONF=no
4. ZEROCONF=yes
```

이 문제는 처음 보몀 `YES/NO`가 반대로 느껴져서 헷갈립니다. 핵심은 `169.254.0.0/16`이 무엇인지와 `NOZEROCONF`를 어떻게 읽는지입니다.

`169.254.0.0/16` 대역은 **Zeroconf(제로 설정 네트워크)**에서 사용하는 링크 로컬 주소 대역입니다.  
DHCP 등으로 정상적인 IP를 받지 못했을 때 별도의 설정 없이 같은 네트워크 안에서 통신할 수 있도록 자동으로 사용하는 주소라고 보면 됩니다.

```
169.254.0.0 ~ 169.254.255.255
        ↓
Zeroconf에서 사용하는 주소 대역
```

문제의 `route -n` 결과에도 이 경로가 자동으로 들어가 있습니다.
```
169.254.0.0   0.0.0.0   255.255.0.0   U
```

문제에서는 이 `169.254.0.0/16` 라우팅을 없애고 싶다고 했습니다.
그러면 **Zeroconf를 사용하지 않도록 설정**해야 합니다.

여기서 변수 이름을 그대로 한글로 읽어보면 답이 바로 나오게 됩니다.
```
NO ZEROCONF
│    │
│    └─ Zeroconf
└────── 사용하지 않음
```

즉 `NOZEROCONF=yes`는 **"Zeroconf를 사용하지 않겠습니까?" -> YES** 라는 느낌입니다.

그래서 
```
NOZEROCONF=yes
→ Zeroconf 사용 안 함
→ 169.254.0.0/16 자동 라우팅 생성 안 함
```

반대로 1번은 `NOZEROCONF=no`니깐 "Zeroconf를 사용하지 않을 거야?" -> 아니 결국 Zeroconf를 사용하는 쪽이 되므로 원하는 설정이 아닙니다.  
문제에 있는 명령도 같이 희석해보면 
```
cat << __EOF__ >> /etc/sysconfig/network
> NOZEROCONF=yes
> __EOF__
```

이건 `/etc/sysconfig/network` 파일 뒤에 `NOZEROCONF = yes`라는 한 줄을 **추가하라**는 뜻입니다.

### Zeroconf에 대해서
169.254.0.0/16 = Zeroconf인게 아니라, 169.254.0.0/16을 자동으로 사용하는 기능이 Zeroconf를 구성하는 한 부분입니다.

먼저 `Zeroconf`라는 이름부터 풀어보면 
```
Zero Configuration
= 설정(Configuration)을 거의 0으로 해도
  네트워크가 어느 정도 동작하게 하자
```

원래 컴퓨터가 네트워크에서 통신하려면 여러 설정이 필요합니다.
```
IP 주소
서브넷 마스크
DNS
호스트 이름
서비스 위치
...
```
보통은 관리자가 직접 설정하거나 DHCP/DNS 서버가 처리해 주게 됩니다.

그런데 Zeroconf의 생각은 이겁니다.
> "DHCP 서버도 없고, 관리자가 IP를 설정하지 않아도 같은 네트워크에 연결된 장비끼리는 알아서 통신하게 해보자."

그래서 Zeroconf에는 몇  가지 자동화 기능이 들어가는데, 그중 하나가 **자동 IP 주소 설정**입니다.
```
Zeroconf
├─ IP 주소 자동 설정
├─ 이름을 자동으로 찾기
└─ 네트워크 서비스를 자동으로 찾기
```

여기서 IPv4의 **IP 주소 자동 설정**에 사용되는 주소가 바로 `169.254.0.0/16` 입니다.  
즉 연결은 다음과 같이 되는 것입니다.
```
컴퓨터가 네트워크에 연결됨
        ↓
DHCP 서버가 없음
또는 IP를 못 받음
        ↓
그래도 같은 LAN의 다른 장비와 통신하고 싶음
        ↓
스스로 169.254.x.x 주소를 잡음
        ↓
같은 Link 안에서 통신
```

이런 "사람이 IP를 직접 설정하지 않았는데도 자동으로 네트워크를 구성한다"는 행동이 Zeroconf의 철학인 거야.

## 문제 16번 : 정답 4

```
"다음 중 (    ) 안에 들어갈 내용으로 알맞은 것은?"

각각의 응용 프로그램은 할당된 포트를 이용해
통신할 데이터를 주고받는다.

포트는 번호로 관리되고, 0번부터 (ㄱ)번까지는
잘 알려진 포트(Well-known Port)라 하여
주로 시스템에서 사용하고 있다.

리눅스에서는 (ㄴ) 파일에서 주요 포트 번호를 확인할 수 있다.

1. ㄱ : 128,   ㄴ : /etc/protocols
2. ㄱ : 1024,  ㄴ : /etc/protocols
3. ㄱ : 65536, ㄴ : /etc/services
4. ㄱ : 1023,  ㄴ : /etc/services
```

이 문제는 **포트 번호의 범위**와 **리눅스에서 포트 번호 정보를 어디서 확인하는지**를 묻는 문제이다.  
먼저 포트부터 아주 쉽게 보면 **포트 = 한 컴퓨터 안에서 어떤 프로그램과 통신할지 구분하는 번호**라고 보면 된다.

예를 들어 서버 한 대가 있어도 여러 프로그램이 동시에 네트워크를 쓰잖아
```
웹 서버      → 80번 포트
SSH 서버     → 22번 포트
FTP 서버     → 21번 포트
DNS 서버     → 53번 포트
```

IP 주소가 **어느 컴퓨터인지** 알려준다면, 포트 번호는 **그 컴퓨터 안에서 어느 프로그램인지**알려주는 번호입니다.

### Well-known Port 범위
포트 번호는 전체적으로 `0 ~ 65535` 까지 있습니다. 그중 `0 ~ 1023`이 Well-known Port입니다.

즉 문제의 0번부터 (ㄱ)번까지에서 ㄱ = 1023이 되는 것입니다. 대표적인 Well-known Port를 보면 
```
20/21 → FTP
22    → SSH
23    → Telnet
25    → SMTP
53    → DNS
80    → HTTP
110   → POP3
443   → HTTPS
```

### 왜 1024가 아니라 1023인가.

이 부분이 자주 헷갈립니다. 범위가 0 ~ 1023이면 총 개수는 1024개  
즉 
```
Well-known Port 개수 = 1024개
마지막 번호 = 1023
```

### /etc/services
리눅스에서 주요 서비스 이름과 포트 번호를 `/etc/services` 파일에서 확인할 수 있습니다.  
예를 들어 이런 식으로 들어 있습니다.
```
ssh      22/tcp
telnet   23/tcp
smtp     25/tcp
domain   53/tcp
http     80/tcp
https    443/tcp
```

```
4. 256
```

이 문제는 아까 B 클래스 문제에서 나왔던 `-3` 계산 방식이 그대로 적용된 겁니다.

C 클래스의 기본 넷마스크가 `255.255.255.0 = /24` 이니까 IPv4 전체 32비트 중에서 
네트워크 부분 24비트, 호스트 부분 8비트가 남게 됩니다.

호스트 부분이 8비트이기 때문에 만들 수 있는 전체 IP 주소는 2^8 = 256개 입니다.  
그런데 이 256개를 전부 PC에 줄 수는 없습니다.

```
전체 주소          256개

네트워크 주소       -1
브로드캐스트 주소    -1
----------------------
일반적인 사용 가능 IP
                  254개
```

여기까지만 보면 3번 254개가 맞아 보입니다.

그런데 문제에는 다음과 같은 조건이 있습니다. 
> 인터넷에 연결시키려 한다.  
인터넷으로 나가렴녀 이 서브넷에서 **라우터의 게이트웨이 IP 하나**가 필요하다고  
이 문제에서는 계산하는 것입니다.

예를 들어 
```
192.168.1.0     → 네트워크 주소
192.168.1.1     → 게이트웨이
192.168.1.2     → PC
192.168.1.3     → PC
...
192.168.1.254   → PC
192.168.1.255   → 브로드캐스트
```

그러면 실제 일반 호스트에게 줄 수 있는 주소는 

```
256
- 네트워크 주소 1
- 브로드캐스트 주소 1
- 게이트웨이 주소 1
= 253
```

그래서 정답은 253개 입니다.

## 문제 20번 : 정답 2

```
"다음 중 netstat의 state 결과 값에 대한 설명으로 틀린 것은?"

1. LISTEN
   : 서버로 들어오는 패킷을 위해 소켓을 열고 기다리는 상태

2. CLOSE-WAIT
   : 원격 호스트가 종료되고 소켓도 종료된 상태

3. ESTABLISHED
   : 3way-handshaking이 완료 후 서버와 클라이언트가
     서로 연결된 상태

4. TIME-WAIT
   : TCP 프로토콜의 연결 종료 과정에서 마지막 FIN 신호에 대한
     ACK 전달 후 최종 Close까지
     2MSL(Maximum Segment Life Time) 동안 대기하는 상태
```

| 상태             | 의미                                         | 쉽게 말하면                         |
| -------------- | ------------------------------------------ | ------------------------------ |
| `LISTEN`       | 서버가 클라이언트의 연결 요청을 기다리는 상태                  | “접속 요청 기다리는 중”                 |
| `SYN_SENT`     | 클라이언트가 SYN을 보내고 응답을 기다리는 상태                | “연결해도 돼?” 보내고 기다리는 중           |
| `SYN_RECEIVED` | SYN을 받고 SYN+ACK를 보낸 뒤 마지막 ACK를 기다리는 상태     | “좋아, 연결하자. 너도 확인해줘”            |
| `ESTABLISHED`  | 3-way handshake가 끝나 정상 연결된 상태              | “서로 연결 완료”                     |
| `FIN_WAIT_1`   | 내가 먼저 FIN을 보내고 상대의 응답을 기다리는 상태             | “나 이제 끊을게”                     |
| `FIN_WAIT_2`   | 내가 보낸 FIN에 대한 ACK는 받았고, 상대의 FIN을 기다리는 상태   | “나는 끊을 준비 끝, 너도 끊는다고 말해줘”      |
| `CLOSE_WAIT`   | 상대가 FIN을 보냈지만 내 프로그램이 아직 연결을 닫지 않은 상태      | “상대는 끊겠대, 나는 아직 정리 중”          |
| `LAST_ACK`     | 상대의 FIN을 받은 뒤 나도 FIN을 보내고 마지막 ACK를 기다리는 상태 | “나도 끊을게, 마지막 확인 기다리는 중”        |
| `TIME_WAIT`    | 마지막 ACK를 보낸 뒤 2MSL 동안 기다리는 상태              | “연결은 끝났지만 혹시 남은 패킷이 있나 기다리는 중” |
| `CLOSING`      | 양쪽이 거의 동시에 FIN을 보낸 상태                      | “둘 다 동시에 끊겠다고 한 상태”            |
| `CLOSED`       | 연결이 완전히 종료된 상태                             | “완전히 끝남”                       |
