## 제 1절 데이터 모델의 이해

> 데이터 모델링 = 현실 세계의 사람, 사물, 업무와 그 관계를 데이터베이스에서 저장할 수 있는 구조로 표현하는 작업
> 데이터 모델링은 DB 구축만을 위한 것이 아니라 업무를 이해 · 분석 · 표현하고, 그 결과를 DB 설계와 개발에 사용하는 작업이다.

### 1. 데이텉 모델이란?

현실 세계의 데이터를 어떤 구조로 저장할지 표현한 설계도 이며 데이터 모델링은 그 설계도를 만드는 과정이라고 할 수 있습니다.

즉 

```
데이터 모델   = 결과물
데이터 모델링 = 만드는 과정
```

건축으로 비교하면
```
건축 설계도     = 데이터 모델
설계도를 그리는 일 = 데이터 모델링
실제 건물       = 데이터베이스
```

이렇게 이해하면 됩니다.

### 2. 왜 데이터 모델링을 하는가?

현실의 정보를 그냥 DB에 막 집어넣으면 문제가 생깁니다.

예를 들어 : 

| 학생 | 학과     | 학과전화번호  |
| -- | ------ | ------- |
| 철수 | 컴퓨터공학과 | 02-1111 |
| 영희 | 컴퓨터공학과 | 02-1111 |
| 민수 | 컴퓨터공학과 | 02-1111 |

컴퓨터공학과 전화번호가 계속 중복됩니다. 나중에 전화번호가 바뀌면 세 줄 전부 수정해야 합니다.
그래서 모델리을 통해 

```
학생
철수 → 컴퓨터공학과
영희 → 컴퓨터공학과
민수 → 컴퓨터공학과

학과
컴퓨터공학과 → 02-1111
```

처럼 구조를 잡습니다.

따라서 목적은 크게 **중복을 줄이고, 데이터 관계를 명확하게 하고, 데이터를 정확하게 관리하기 위해서**입니다.   
이게 데이터 모델링의 유의점 3가지입니다.

- 중복성(Duplication): **같은 데이터를 여러 곳에 반복 저장하지 않도록 한다.**
- 비유연성(Inflexibility): **업무가 조금 바뀌었다고 데이터 모델 전체를 크게 수정하지 않도록 설계한다.**
- 비일관성(Inconsistency): **같은 의미의 데이터가 서로 다른 값으로 존재하지 않도록 한다.**

SQLP 1과목을 공부할 때는 결국 이 세 가지를 이해해야 합니다.

```
무엇이 있는가?     → 엔터티(Entity)
어떤 정보를 가지나? → 속성(Attribute)
서로 어떻게 연결되나? → 관계(Relationship)
```

### 3. 데이터 모델링의 3단계
> 개념적 → 논리적 → 물리적  
> 무엇이 필요한가 → 어떻게 구조화할까 → DB에 어떻게 만들까  
> 개념적 = 무엇이 있는지 큰 그림 그리기

#### 개념적 데이터 모델링
> 업무에 무엇이 필요한지 큰 그림을 그리는 단계

아직 컬럼 타입이나 인덱스 같은 것 생각하지 않았습니다.

예를 들어 쇼핑몰이라면 

```
고객 - 주문 - 상품
```

정도로 먼저 생각합니다.

"고객이 있고, 상품이 있고, 고객이 상품을 주문하는구나."

즉 **업무 자체를 이해하는 단계**입니다.

#### 논리적 데이터 모델링
> 큰 그림을 실제 데이터 구조처럼 자세하게 만드는 단계  
> 논리적 = 엔터티 안을 자세히 설계하고 정규화하기

개념적 단계에서 

```
고객 - 주문 - 상품
```

까지만 만들었다면 이제 자세히 정의합니다.

```
고객
- 고객번호
- 고객명
- 이메일

주문
- 주문번호
- 고객번호
- 주문일자

상품
- 상품번호
- 상품명
- 가격
```

그리고 여기서 

```
PK는 무엇인가?
FK는 무엇인가?
속성은 무엇인가?
관계는 1:M인가?
중복 데이터는 없는가?
정규화가 필요한가?
```
를 결정합니다.

#### 물리적 데이터 모델링
> 논리적으로 만든 설계도를 실제 DB에 만들 수 있게 바꾸는 단계

이제 Oracle, MySQL 같은 실제 DBMS를 생각합니다.

논리 모델:

```
고객번호
고객명
가입일자
```

↓

물리 모델:

```
CUSTOMER_ID   VARCHAR2(10) PRIMARY KEY
CUSTOMER_NAME VARCHAR2(100) NOT NULL
JOIN_DATE     DATE
```

그리고:

```
VARCHAR2를 쓸까?
NUMBER를 쓸까?
인덱스는 어디에 만들까?
파티션을 사용할까?
테이블명/컬럼명은?
성능은 어떻게 할까?
```
같은 걸 결정합니다.


### 4. 스키마(Schema)의 3단계 구조
스키마는 **데이터베이스를 어떤 관점에서 바라보는지 나눈 설계 단계**라고 이해하면 됩니다.
가장 쉽게 설명하자면

> 스키마 = 데이터베이스의 구조를 설명하는 설계도

#### 외부 스키마
> 사용자마다 보이는 화면

예를 들어 같은 학교 DB라도 
```
학생이 보는 것
- 이름
- 학년
- 성적

교수가 보는 것
- 학생명
- 수강과목
- 성적

관리자가 보는 것
- 학생 전체 정보
```
처럼 사람마다 필요한 정보가 다릅니다.

즉 **외부 스키마 = 사용자별로 필요한 부분만 보여주는 구조**

#### 개념 스키마
> 데이터베이스 전체 구조

예를 들어 
```
학생
과목
수강
교수
학과
```
그리고 이들이 어떻게 연결되는지 전체적으로 정의합니다.  
쉽게 정리하자면 **개념 스키마 = 우리 DB 전체 설계도**

#### 내부 스키마
> 데이터를 실제 컴퓨터에 어떻게 저장할지 정하는 구조

예
```
어떤 파일에 저장할까?
어떤 인덱스를 만들까?
어떤 블록에 저장할까?
저장 순서는?
```

즉 **내부 스키마 = 실제 저장 방법**

### 5. 데이터 독립성
#### 논리적 데이터 독립성
> 개념 스키마가 바뀌어도 외부 스키마가 영향을 덜 받는 것

#### 문리적 데이터 독립성
> 내부 저장 구조가 바뀌어도 개념 스키마가 영향을 덜 받는 것

### 6. 데이터 모델링의 유의점
- 중복성(Duplication): **같은 데이터를 여러 곳에 반복 저장하지 않도록 한다.**
- 비유연성(Inflexibility): **업무가 조금 바뀌었다고 데이터 모델 전체를 크게 수정하지 않도록 설계한다.**
- 비일관성(Inconsistency): **같은 의미의 데이터가 서로 다른 값으로 존재하지 않도록 한다.**

## 제 2절 엔터티(Entity)

### 1. 엔터티란?
- 엔터티는 같은 종류의 **여러 대상**을 한곳에 모아서 관리하기 위해 만든 이름표 같은 것입니다.
- 예: 학생, 상품, 주문

### 2. 엔터티 · 인스턴스 · 속성 구분
- 엔터티: 관리 대상의 종류
- 인스턴스: 실제 데이터 한 건
- 속성: 인스턴스를 설명하는 정보

### 3. 엔터티의 특징
- 업무에서 필요한 정보여야 함
- 식별할 수 있어야 함
- 2개 이상의 인스턴스를 가져야 함
- 업무 프로세스에서 사용되어야 함
- 속성을 가져야 함
- 다른 엔터티와 관계를 가지는 것이 일반적임

### 4. 엔터티의 분류
- 기본 엔터티 : 원래 있는 것
- 중심 엔터티 : 없무의 중심이 되는 것
- 행위 엔터티 : 업무를 하면서 생긴 기록

| 분류     | 쉽게                  | 예                |
| ------ | ------------------- | ---------------- |
| 기본 엔터티 | 원래 존재하는 기본 대상       | 사원, 고객, 상품       |
| 중심 엔터티 | 핵심 업무가 발생하면서 생김     | 주문, 계약, 사고       |
| 행위 엔터티 | 업무를 수행하면서 생기는 상세 기록 | 주문상세, 계약진행, 결제내역 |

> 인스턴스란?  
> 엔터티에 실제로 들어 있는 데이터 한 건

## 제 3절 속성(Attribute)
### 1. 속성이란?
- 속성은 **엔터티 안의 인스턴스를 설명해주는 정보 항목**입니다.
- 쉽게 말하면 **"이 대상에 대해 무엇을 저장할 것인가?"**입니다.
- 예 : 학생의 `학생번호`, `이름`, `학년`, `생년월일`
    ```
        학생 ← 엔터티

        학생번호
        이름
        학년
        생년월일
        ↑
        속성
    ```

    예를 들어

    | 학생번호 | 이름 | 학년 |
    | ---- | -- | -: |
    | 1001 | 철수 |  2 |

    여기서 

    학생        → 엔터티
    철수        → 인스턴스
    이름        → 속성
    '철수'      → 속성값

    핵심은 

    **엔터티 = 무엇을 관리할까?**
    **속성 = 그 대상의 무엇을 기록할까?**

### 2. 엔터티 · 인스턴스 · 속성 · 속성값
| 구분   | 쉽게          | 예      |
| ---- | ----------- | ------ |
| 엔터티  | 관리 대상의 종류   | 학생     |
| 인스턴스 | 실제 데이터 한 건  | 철수     |
| 속성   | 대상을 설명하는 항목 | 이름, 학년 |
| 속성값  | 실제 저장된 값    | 철수, 2  |

### 3. 속성의 특징

속성은 다음 특징을 가집니다.

- 업무에서 실제로 필요한 정보여야 함
- 하나의 속성은 하나의 의미를 가져야 함
- 하나의 인스턴스에서 하나의 속성은 하나의 값을 가져야 함
- 엔터티를 설명할 수 있어야 함
- 속성값은 정해진 범위 안의 값을 가져야 함

쉽게 말하면 **속성 하나에는 한 가지 뜻의 값 하나만 넣는다.**

예:

```
이름 = 철수        ✅
전화번호 = 010-1111 ✅
```

이런 식으로 하나의 속성에 너무 많은 의미를 섞으면 안 됩니다.

### 4. 속성의 분류
속성은 보통 **기본 속성, 설계 속성, 파생 속성**으로 나뉩니다.

| 분류    | 쉽게                 | 예            |
| ----- | ------------------ | ------------ |
| 기본 속성 | 원래부터 존재하는 정보       | 이름, 생년월일, 가격 |
| 설계 속성 | 시스템을 만들면서 새로 만든 정보 | 학생번호, 주문번호   |
| 파생 속성 | 다른 값을 계산해서 만든 정보   | 나이, 총금액      |

#### 기본 속성
> 원래 업무에서 가지고 있던 정보

예
```
학생
- 이름
- 생년월일
```
이름, 생년월일은 원래 존재하는 정보입니다.

#### 설계 속성
> 관리하기 편하게 우리가 새로 만든 정보

예
```
학생번호 = 1001
주문번호 = ORD001
```
사람이 태어날 때 학생번호를 가지고 태어나는 건 아니죠.

#### 파생 속성
> 다른 속성을 계산해서 만든 값

예
```
가격 = 10,000
수량 = 3

총금액 = 30,000
```
총금액은 가격 × 수량으로 만들어졌으므로 파생 속성입니다.

### 5. 도메인 (Domain)
도메인은 **그 속성에 들어갈 수 있는 값의 범위** 입니다.

### 6. 속성을 판단하는 가장 쉬운 방법
어떤 단어가 나왔을 때, **이게 관리 대상 자체인가, 아니면 그 대상을 설명하는 정보인가?**를 보면 됩니다.

예 
```
상품
- 상품번호
- 상품명
- 가격
- 재고수량
```

- 상품 → 엔터티
- 상품명 → 속성
- 가격 → 속성
- 재고수량 → 속성

## 제 4절 관계(Relationship)
### 1. 관계란?
관계는 **두 개 이상의 엔터티가 서로 어떤 관련이 있는지를 나타내는 것**입니다.  
쉽게 말하면 **"누가 누구와 어떤 관계인가?"**를 표현합니다.

예
```
학생 ── 수강한다 ── 과목
고객 ── 주문한다 ── 상품
사원 ── 소속된다 ── 부서
```

여기서 
- 학생, 과목 -> 엔터티
- 수강한다 -> 관계

즉 한 줄로 정리하면 관계 = 엔터티와 엔터티를 연결해주는 의미

### 2. 관계를 왜 만드는가? 
현실의 데이터는 혼자 떨어져 있지 않고 서로 연결되어 있기 때문입니다. 

예를 들어
```
학생
- 학생번호
- 이름

학과
- 학과코드
- 학과명
```
학생과 학과가 따로만 있으면 "이 학생이 어느 학과에 다니는지" 알 수 없습니다.  
그래서 관계를 만듭니다.

학생 - 소속된다 - 학과  
즉 **관계는 데이터끼리 어떻게 연결되어 있는지를 알려줍니다.**

### 3. 관계의 종류

관계는 크게 **존재에 의한 관계**와 **행위에 의한 관계**로 볼 수 있습니다.
| 구분    | 쉽게            | 예            |
| ----- | ------------- | ------------ |
| 존재 관계 | 원래 서로 연결되어 있음 | 사원은 부서에 소속된다 |
| 행위 관계 | 어떤 행동 때문에 연결됨 | 고객이 상품을 주문한다 |

#### 존재에 의한 관계
> 서로 존재 자체로 연결되는 관계

예
```
사원 ── 소속된다 ── 부서
학생 ── 소속된다 ── 학과
```

#### 행위에 의한 관계
> 어떤 행동이 발생해서 만들어지는 관계

예:
```
고객 ── 주문한다 ── 상품
학생 ── 수강한다 ── 과목
```

### 4. 관계의 차수(Cardinality)
관계에서 가장 중요한 건 **한쪽 데이터 하나가 반대쪽 데이터 몇 개와 연결될 수 있는가?** 입니다.

`1 : 1`

```
사람 1 ─── 1 주민등록증
```

한 사람에게 주민등록증 하나.

하나 ↔ 하나

`1 : M`

```
부서 1 ─── M 사원
```

하나의 부서에 여러 사원이 있을 수 있습니다.

하나 ↔ 여러 개

`M : N`

```
학생 M ─── N 과목
```

한 학생은 여러 과목을 들을 수 있고, 한 과목도 여러 학생이 들을 수 있습니다.

여러 개 ↔ 여러 개

실제 DB에서는 보통 중간 엔터티를 만들어 풀어냅니다.

학생 ── 수강 ── 과목

### 5. 관계의 선택성(Optionality)

이건 앞에서 봤던 ○, |, 까치발과 연결됩니다.

반드시 관계가 있어야 하는가, 없어도 되는가?

예:
```
고객 1 ─── ○< 주문
```

뜻:

고객은 주문을 0번 할 수도 있고 여러 번 할 수도 있음

쉽게 보면:

| 기호  | 의미        |            |
| --- | --------- | ---------- |
| `○` | 없어도 됨 = 0 |            |
| `   | `         | 반드시 있음 = 1 |
| 까치발 | 여러 개 = N  |            |


그래서:

```
○| → 0 또는 1
|| → 정확히 1
|< → 1개 이상
○< → 0개 이상
```
입니다.

### 6. 관계를 판단하는 방법

어떤 두 엔터티가 있으면 이렇게 질문하면 됩니다.

-  둘이 서로 관련이 있나?
- 어떤 의미로 연결되나?
- 한쪽 하나가 반대쪽 몇 개와 연결되나?
- 반드시 연결되어야 하나, 없어도 되나?

예:
```
고객 ── 주문 ── 상품
```
질문하면:

```
고객과 주문은 관련 있나? → O
어떤 관계? → 고객이 주문한다
고객 1명이 주문 여러 개 가능? → O
주문이 없는 고객도 가능? → O
```

따라서:

```
고객 1 ─── ○< 주문
```

처럼 표현할 수 있습니다.

### 7. 관계의 표기법
관계명, 관계차수(Cardinality), 관계선택사양(Optionality)을 봅니다.

## 제 5절 식별자

### 1. 식별자란?
- 식별자는 **엔터티 안에서 각각의 인스턴스를 구별할 수 있게 해주는 속성**입니다.
- 쉽게 말하자면 **"이 데이터가 정확히 누구인지 알려주는 번호표"**입니다.

예를 들어 학생 엔터티가 있다고 해보겠습니다.

| 학생번호 | 이름 | 학년 |
| ---: | -- | -: |
| 1001 | 철수 |  1 |
| 1002 | 철수 |  2 |
| 1003 | 영희 |  1 |

`이름`만 보면 `철수`가 두 명이라 누가 누구인지 알 수 없습니다.

하지만 

```
학생번호 1001 → 철수
학생번호 1002 → 철수
```

처럼 `학생번호`를 정확하게 구별할 수 있습니다.  
식별자 = 인스턴스를 유일하게 구별하는 이름표

DB 테이블로 구현하면 주식별자는 보톤 Primary Key(PK)와 연결됩니다.

### 2. 왜 식별자가 필요한가?
같은 이름이나 같은 값을 가진 데이터가 있을 수 있기 때문입니다.

예
```
철수
철수
철수
```

이렇게만 있으면 누가 누군지 모릅니다.  
그래서

```
1001 → 철수
1002 → 철수
1003 → 철수
```
처럼 각각을 구별할 수 있는 값을 만듭니다.  
간단하게 말하자면 **같은 사람이 여러 명 있어도 정확히 한 명을 찾기 위해서 사용한다.**

### 3. 주식별자의 특징
**유**일성, **최**소성, **불**변성, **존**재성

#### 유일성
> 같은 식별자 값이 두 개 있으면 안 된다.

```
1001 → 철수
1002 → 영희     ✅
```

이건 안 됩니다.
```
1001 → 철수
1001 → 영희     ❌
```

1001이 누구인지 구분할 수 없기 때문입니다.
> 유일성 = 하나만 있어야 함

#### 최소성
> 꼭 필요한 속성만 식별자로 사용한다.

예를 들어 `학생번호` 하나만으로 학생을 구별할 수 있는데

```
학생번호 + 이름 + 학년
```

을 전부 식별자로 사용할 필요는 없습니다.

```
학생번호
```

하나면 충분합니다.

> 최소성 = 필요 없는 것은 빼기

#### 불변성
> 한 번 식별자로 정했으면 자주 바뀌면 안 된다.

예를 들어 

```
학생 번호 1001
```

이 오늘은 `1001`, 내일은 `8888`처럼 계속 바뀌면 다른 테이블에서도 연결하기 어렵습니다.

> 불변성 = 웬만하면 바뀌지 않아야 함

#### 존재성
> 식별자 값은 반드시 있어야 된다.

즉 
```
학생번호 = NULL ❌
```

누구인지 식별해야 하는데 번호가 없으면 안 되기 때문입니다. 
> 존재성 = NULL이면 안 됨

### 4. 식별자의 분류
| 구분 기준       | 종류            |
| ----------- | ------------- |
| 대표성         | 주식별자 / 보조식별자  |
| 스스로 만들어졌는가  | 내부식별자 / 외부식별자 |
| 속성 개수       | 단일식별자 / 복합식별자 |
| 원래 존재하던 값인가 | 본질식별자 / 인조식별자 |

### 5. 주식별자와 보조식별자 
#### 주식별자
> 여러 식별자 중 대표로 선택한 식별자

예 :
```
학생번호 -> 주식별자
```
DB에서는 보통 PK가 됩니다.

#### 보조식별자
> 학생을 구별할 수는 있지만 대표로 선택되지 않은 식별자

예
```
학생번호
주민등록번호
```
둘 다 학생을 구별할 수 있다고 해보겠습니다.

`학생번호`를 주식별자로 선택했다면
```
학생번호     → 주식별자
주민등록번호 → 보조식별자
```
가 될 수 있습니다.
> 주 = 대표 선수 / 보조 = 후보였지만 대표가 아닌 선수

### 6. 내부식별자와 외부식별자
#### 내부 식별자
> 자기 엔터티 안에서 만들어진 식별자

예
```
학생
- 학생번호(FK)
```

`학생번호`는 학생 엔터티 자체의 식별자입니다.

#### 외부식별자
> 다른 엔터티의 식별자를 가져온 것

예 
```
학과
- 학과코드(PK)

학생
- 학생번호(PK)
- 학과코드(FK)
```

학생의 `학과코드`는 학과 엔터티에서 가져왔습니다.

외부식별자는 DB에서 보통 FK와 연결해서 이해하면 쉽습니다. 

### 7. 단일식별자와 복합식별자
#### 단일 식별자
> 속성 하나만으로 구별

예
```
학생번호
```

하나만으로 학생을 구별합니다.

#### 복합식별자
> 속성 여러 개를 합쳐야 구별

예
```
주문상세

주문번호 + 상품번호
```

주문번호만으로는 상품 하나를 특정할 수 없고, 상품번호만으로도 어떤 주문인지 알 수 없습니다.  

둘을 합쳐야
```
(주문번호, 상품번호)
```
하나의 주문상세를 구별할 수 있습니다.

### 8. 본질식별자와 인조식별자
#### 본질식별자
> 업무에서 원래 존재하던 의미 있는 값을 식별자로 사용

예
```
사원번호
주문번호
```

#### 인조식별자
> 관리하기 편하게 새로 만든 식별자

예 
```
ID = 1
ID = 2
ID = 3
```

혹은

```
AUTO_INCREMENT
SEQUENCE
UUID
```
