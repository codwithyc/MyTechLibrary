## 문제 1번 : 정답 1번
```
"다음 ( ) 안에 들어갈 내용으로 알맞은 것은?"

[root@localhost ~] #cat sample
#!/bin/bash
var=0
cnt=$0
while [ "$var" -le (ㄱ)]
do
var='expr $var + 1'
echo $var
[root@localhost ~] # ./sample
(ㄴ)

1. ㄱ ${#cnt}, ㄴ 9
2. ㄱ "$cnt", ㄴ 9
3. ㄱ ${#cnt}, ㄴ 10
4. ㄱ "$cnt", ㄴ 10
```

이번 문제를 자연어로 바꾸면 이렇게 읽을 수 있습니다.

> `var`라는 변수에 0을 넣는다  
> `cnt`라는 변수에는 현재 실행한 스크립트의 이름을 넣는다.  
> `var`가 `cnt`의 문자열 길이보다 작거나 같은 동안 반복한다.  
> 반복할 때마다 `var`를 1 증가시키고 출력한다. 
아
우선 이런 문제들을 이해하기 위해서는 몇몇 사용방법에 대해서 알아야 됩니다. 

`$`는 **"상자 안의 값을 꺼내라"**라고 생각하면 됩니다.  
예를 들어
```
name="유찬"
```
그러면 `name`이라는 상자 안에 `유찬`이 들어가게 됩니다.

```
name 상자
┌──────┐
│ 유찬 │
└──────┘
```
이때
```
$name
```
은 `name` 상자 안의 값을 꺼내라 라는 뜻이라서 결과는 `유찬`입니다.  
그리고 `$0`은 Bash가 미리 만들어 둔 **특별한 상자**입니다.

스크립트를 이렇게 실행하면 
```
./sample
```
Bash가 자동으로
```
$0 = ./sample
```
이라고 기억하면 됩니다. 

그래서 `cnt=$0`은 `$0` 안에 있는 `./sample`을 꺼내서 cnt라는 새 상자에 넣어라는 뜻입니다.

while은 아주 쉽게 **"조건이 참이 동안 계속 반복해."**라는 뜻입니다.  
예를 들어 `while [ "$var" -le 8 ]` 이라고 되어 있으면 한국말로 var가 8보다 작거나 같은 동안 계속 반복해 라는 뜻입니다.

- cnt        → 변수 이름
- $cnt       → cnt 안의 값
- ${#cnt}    → cnt 안의 값의 길이

## 문제 2 : 정답 1번
```
"다음에서 설명하는 데몬 관련 유틸리티로 알맞은 것은?"

리눅스 서비스의 시작, 정지 재시작 등을 제어하는 명령어로 레드햇 계열 7부터 기본 명령어로 사용된다.

1. systemctl
2. chkconfig
3. ntsysv
4. service
```

### systemctl
`systemctl`은 systemd를 제어하는 명령어입니다.  
`systemd`가 관리하는 여러 시스템 자원(Unit)을 조회하고 제어하는 명령어라고 보면 됩니다.

먼저 `systemd` 부터 모면, 리눅스가 부팅된 뒤에 이런 것들을 관리하는 **시스템 관리자**입니다.

- 어떤 서비스를 실행할지
- 어떤 서비스를 중지할지
- 부팅할 때 무엇을 자동으로 실행할지
- 어떤 서비스가 죽으면 다시 실행할지
- 특정 시간에 무엇을 실행할지
- 디스크를 어디에 마운트할지
- 시스템이 어떤 부팅 상태로 들어갈지

즉 `systemd`는 리눅스 시스템 전체의 실행 상태를 관리합니다. 그리고 `systemctl`이 `systemd`에게 명령을 내리는 도구인 겁니다.

#### systemctl이 실제로 제어하는 것
`systemd`는 관리 대상을 Unit(유닛)이라는 단위로 관리합니다.

| Unit 종류    | 역할                 |
| ---------- | ------------------ |
| `.service` | 서비스/데몬             |
| `.socket`  | 소켓                 |
| `.timer`   | 예약 작업              |
| `.mount`   | 파일 시스템 마운트         |
| `.target`  | 여러 Unit을 묶은 시스템 상태 |
| `.path`    | 특정 파일/디렉터리 변화 감시   |

그래서 `systemctl`은 사실 **서비스만 관리하는 명령어가 아닙니다.**

##### 서비스 관리
가장 많이 사용하는 기능
```
systemctl start nginx
systemctl stop nginx
systemctl restart nginx
systemctl status nginx
```

의미

```
start   → 지금 시작
stop    → 지금 중지
restart → 다시 시작
status  → 현재 상태 확인
```
### 왜 Red Hat 7부터라고 하나?
Red Hat 계열은 예전에는 SysV init 기반의 `service`, `ckconfig` 같은 명령을 많이 사용했습니다.  
그러다가 RHEL 7부터 `systemd`가 기본 init 시스템이 되면서 `systemctl` 으로 변경되게 된겁니다.

### chkconfig
`chkconfig`는 예전 Red Hat 계열에서 **서비스가 부팅할 때 자동으로 시작할지 설정**할 때 많이 사용했습니다.
예를 들어 `chkconfig httpd on` -> 부팅 시 httpd 자동 시작 `chkconfig httpd off` -> 자동 시작 해제  

즉 `chkconfig`는 옛날 자동 시작 설정이라고 보면 됩니다.

### ntsysv
`ntsysv`는 예전 Red Hat 계열에서 **"부팅할 때 어떤 서비스를 자동으로 켤지"** 체크박스로 설정하는 도구입니다.  
핵심은 `systemctl` 처럼 명령어를 직접 길게 치는 방식이 아니라, **터미널 안에 메뉴 화면을 띄워서 선택한다**는 점입니다.

예를 들어 `ntsysv`를 실행하면 대략 이런 느낌의 화면이 나옵니다.
```
서비스 설정

[*] sshd
[*] crond
[ ] httpd
[ ] vsftpd
[*] network

        <확인>   <취소>
```

여기서
```
[*] sshd
```
라고 체크하면

> "이 서비스는 해당 실행 레벨에서 자동으로 시작하게 해."

라는 뜻이고

```
[ ] httpd
```
처럼 체크를 해제하면 

> "이 서비스는 자동으로 시작하지 마."

라는 뜻입니다.

중요한 건 **`ntsysv`가 지금 당장 서비스를 켜거나 끄는 도구가 주목적은 아니라는 것**입니다.  
예를 들어 `httpd`가 현재 꺼져 있다고 해보겠습니다.  
`ntsysv`에서
```
[*] httpd
```
를 체크했다고 해서 곧바로 Apache가 실행되는 게 아니라, **다음에 해당 runlevel로 들어갈 때 자동으로 실행되도록 설정** 하는 것입니다.


### service
이것도 예전 방식입니다. 

예를 들어 
```
service httpd start
service httpd stop
service httpd restart
```
처럼 서비스를 시작/중지할 수 있었습니다.

## 문제 3번 : 정답 3번
```
"다음 설명에서 두 명령어를 실행한 것과 동일한 결과를 한 번의 명령으로 실행시키고자 할 때 알맞은 것은?"

# which groups
/user/bin/groups
# ls -l /user/bin/groups
-rwwr-wr-w 1 root 27992 Jun 20 2018
/user/bin/groups

1. ls -l && which groups
2. ls -l grep which groups
3. ls -l $(which groups)
4. ls -l "which groups"
```

일전에 `$` 사용방법에 대해서 작성한 적이 있는데 조금더 상세하게 이해하자면 `$`는 뒤에 **무엇이 붙느냐에 따라 "어떤 값을 꺼내거나 계산해서 넣어라"** 라는 역할을 하게 됩니다.

| 문법                | 의미                                       |
| ----------------- | ---------------------------------------- |
| `$cnt`            | `cnt` 변수의 값을 꺼냄                          |
| `$0`              | Bash가 가진 특별한 값 중 0번, 즉 실행한 스크립트 이름       |
| `${#cnt}`         | `cnt` 값의 글자 수를 구함                        |
| `$(which groups)` | `which groups` **명령을 실행하고 그 출력 결과를 가져옴** |

그렇기 때문에 이번 문제에서는 이 중 `$(명령어)`, 즉 **명령 치환(Command Substitution)을 이해해야 합니다. 

문제는 먼저 다음 명령어를 실행합니다.
```
# which groups
/user/bin/groups
```
`which`는 해당 명령어가 실제로 어느 경로에 존재하는지 찾아주는 명령어입니다. 

따라서 `which groups`는 "`groups` 명령어는 어디에 있나요" 라는 의미이고, 결과가 `/user/bin/groups`라고 나온 것입니다.  
그 다음에는
```
# ls -l /user/bin/groups
```
를 실행합니다.

`ls -l`은 파일의 권한, 소유자, 크기, 날짜 등의 상세 정보를 보여주는 명령어입니다.

즉 문제에서는 원래 다음 **두 단계**를 수행한 것입니다.
```
1. groups 명령어의 위치를 찾음

which groups
↓
/usr/bin/groups


2. 찾은 파일의 상세 정보를 확인

ls -l /usr/bin/groups
```

그런데 문제에서는 이 두 동작을 **한 번의 명령어로 실행하려면 어떻게 해야 하는가?**를 묻고 있습니다.  
여기서 `$(명령어)`를 사용할 수 있습니다.

```
ls -l $(which groups)
```

결과 `/user/bin/groups` 그리고 `$(which groups)` 자리에 그 결과를 넣습니다.  
따라서 `ls -l $(which groups)`는 실제로 다음과 같이 바뀌어서 실행되는 것과 같습니다.

```
ls -l /user/bin/groups
```

### 다른 보기는 왜 틀렸는가?
#### 1번 

`ls -l && which groups` `&&` 는 앞의 명령어가 성공하면 뒤의 명령어를 실행하라는 뜻입니다. 
```
ls -l 실행
↓
성공
↓
which groups 실행
```
두 명령어를 순서대로 실행할 뿐, `which groups`의 결과를 `ls -l`에 넣지는 않습니다.

#### 2번 
```
ls -l grep which groups
```

명령어를 연결하는 기호가 없기 때문에 `grep`, `which`, `groups`를 `ls`의 인자로 취급합니다.

#### 4번
```
ls -l "which groups"
```
큰따옴표 안의 `which groups`는 명령어대로 실행되지 않고 그냥 `which groups`라는 문자열로 처리됩니다.

```

1. 현재 리눅스를 비롯하여 유닉스 대부분이 X11 기반의 X 윈도우 시스템을 사용하고 있다.
2. 디스플레이 장치에 의존적이지 않고 서로 다른 기종을 함께 사용할 수 있다.
3. 윈도 매니저는 그래픽으로 구성된 로그인 유저 인터페이스를 사용자에게 제공하는 역할을 수행하다.

이번 문제는 **X 윈도우에서 각 구성요소가 무슨 역할을 하는지 구분하는 문제**입니다.  

### 먼저 X 윈도우가 무엇인가?

쉽게 정리하자면 **리눅스에서 그래픽 화면을 보여주기 위한 기반 시스템**이라고 보면 됩니다.  
예를 들어 터미널만 있으면 
```
$ ls
$ cd
$ vim
```
이런 문자 화면만 사용하게 되는데,

X 윈도우가 있으면
```
창
버튼
마우스
메뉴
그래픽 프로그램
```
같은 GUI 환경을 만들 수 있습니다.

`X11`은 Window. System의 대표적인 버전이라고 보면 됩니다.  
시험에서는 X Window -> X11로 연결하면 충분합니다. 

다만 실제 최신 리눅스 데스크톱에서는 Wayland도 많이 사용하기 때문에, 이 문장은 현대 기준으로는 조금  
오래된 표현입니다.

> Wayland란?  
> Wayland는 아주 쉽게 말하면 X Window System(X11)을 대신하려고 만든 더 현대적인 화면 처리 방식이야.

### 2번
디스플레이 장치에 의존적이지 않고 서로 다른 기종을 함께 사용할 수 있다.

이것도 맞습니다.  
쉽게 말하자면 "특정 모니터나 특정 컴퓨터에서만 돌아가도록 묶여 있지 않다." 는 뜻입니다.

X Window는 네트워크를 통해서도 동작할 수 있어서
```
컴퓨터 A
→ 프로그램 실행

네트워크

→ 화면 표시
```
같은 구조도 가능합니다.

즉 **프로그램이 실행되는 컴퓨터와 화면이 표시되는 컴퓨터가 달라도 될 수 있다**는게 X Window의 특징입니다.

### 3번
윈도 매니저가 그래픽으로 구성된 로그인 UI를 제공한다.

3번이 틀린 이유는 **로그인 화면을 담당하는 것은 Window Manager가 아니라 Display Manager**입니다.
구분하면
```
Display Manager
→ 로그인 화면 담당

Window Manager
→ 로그인 후 창 관리
```

예를 들어 로그인 화면
```
사용자 이름
비밀번호
[로그인]
```
이런 화면을 보여주는 게 **Display Manager**입니다. 

반면 Window Manager는 로그인한 다음
```
Chrome 창
VS Code 창
터미널 창
```
의 크기, 위치, 이동, 최소화, 최대화, 창 테두리 같은 걸 관리합니다.  
그래서 이 문제의 가장 중요한 한 줄은 **로그인 = Display Manager / 창 관리 = Window Manager** 입니다.

### 4번 
X 윈도우는 서버와 클라이언트가 독립적으로 동작하는 네트워크 지향 시스템이다.

X Window는 Client-Server 구조를 사용하빈다.  
그런데 일반 웹 개발에서 생각하는 서버/클라이언트와는 조금 다르게 느껴질 수 있습니다.

```

```

## 문제 5번 : 정답 1번
```
"systemd에 대한 설명으로 틀린 것은?"

1. /etc/inittab에서 실행 레벨을 변경할 수 있다.
2. 리눅스 커널이 실행하는 첫 번째 프로세스이다.
3. 온디멘드 엑티베이션 기능을 제공한다.
4. Service, Target, Socket와 같은 유닛 단위로 시스템 및 서비스를 관리한다.
```

이번 문제는 먼저 `systemd`와 `systemctl`의 관계를 잡으면 쉬워집니다. 

systemd = 리눅스가 부팅된 뒤 서비스와 시스템 상태를 실제로 관리하는 관리자  
systemctl = 그 systemd에게 명령을 내리는 도구

예를 들어 `systemctl restart nginx` 라고 입력하면 `systemctl`이 직접 nginx를 관리하는 것이 아니라

```
사용자
  ↓
systemctl
  ↓
systemd
  ↓
nginx.service 재시작
```
이렇게 동작한다고 보면 됩니다.

### systemd는 정확히 무엇인가?
컴퓨터가 켜지면 대략 이런 순서로 진행됩니다.
```
컴퓨터 전원 ON
   ↓
부트로더
   ↓
Linux Kernel 실행
   ↓
systemd 실행  ← PID 1
   ↓
필요한 서비스들을 실행
   ├─ sshd
   ├─ nginx
   ├─ NetworkManager
   ├─ cron 계열 작업
   └─ 기타 시스템 기능
```

즉 커널이 올라온 다음 **사용자 공간에서 가장 먼저 실행되어 전체 시스템을 준비하는 프로그램**이 systemd라고 보면 됩니다.  
그래서 `systemd`는 단순히 서비스를 켜고 끄는 것뿐 아니라
- 서비스 시작 / 중지
- 부팅 순서 관리
- 소켓 관리
- 타이머 관리
- 마운트 관리
- 시스템 상태 관리
등을 담당합니다.

### 1. /etc/inittab에서 실행 레벨을 변경할 수 있다.
`/etc/inittab`은 옛날 SysV init 방식에서 사용하던 설정 파일입니다.

과거에는
```
runlevel 3
→ 텍스트 기반 다중 사용자 모드

runlevel 5
→ GUI 다중 사용자 모드
```
처럼 **Runlevel**이라는 숫자로 시스템 상태를 관리했습니다.  
그리고 `/etc/inittab`에서 기본 실행 레벨을 설정하고는 했습니다.

하지만 systemd에는 이 방식을 대신해서 **Target**을 사용합니다.

예를 들어
```
과거 SysV init
Runlevel 3

↓ systemd에서는

multi-user.target
```

그리고 
```
과거 Runlevel 5

↓

graphical.target
```
처럼 대응됩니다.

systemd에서 기본 부팅 Target을 바꾸려면 보통 
```
systemctl set-default multi-user.target
```

또는 

```
systemctl set-default graphical.target
```
처럼 사용합니다.

### 2. 리눅스 커널이 실행하는 첫 번째 프로세스이다.

systemd를 사용하는 시스템에서는 커널이 부팅된 뒤 `systemd`가 PID 1로 실행됩니다.  
`PID`는 Process ID, 즉 프로세스 번호입니다.

```
systemd
PID = 1
```

쉽게 말하자면 **리눅스 사용자 공간 프로세스들의 가장 첫 번째 관리자**라고 보면 됩니다.

### 3. 온디맨드 액티베이션 기능을 제공한다.
`On-Demand Activation`은 이름 그대로 **필요할 때 서비스를 실행한다.**는 뜻입니다.

예를 들어 어떤 서비스가 항상 실행될 필요가 없다고 해보겠습니다.
```
서비스 A

평소
→ 사용 안 함
→ 실행하지 않음

요청 발생!
→ systemd가 서비스 실행
```
즉 시스템을 켜자마자 모든 서비스를 전부 실행시키지 않고, 필요해졌을 때 시작할 수 있습니다.  
대표적으로 systemd의 Socket Activation 같은 방식이 있습니다.

쉽게 정리하자면 "손님도 없는데 직원이 계속 서 있을 필요는 없잖아. 손님 오면 불러." 이런 느낌입니다.

### 4. Service, Target, Socket 같은 Unit 단위로 관리한다
이것도 systemd의 아주 중요한 특징입니다.  
systemd는 관리하는 대상을 **Unit(유닛)** 이라고 부릅니다.

예를 들어
```
nginx.service
sshd.service
multi-user.target
graphical.target
something.socket
backup.timer
```
이런 것들이 전부 Unit입니다.

대표적인 Unit은 

| Unit       | 의미                 |
| ---------- | ------------------ |
| `.service` | 서비스/데몬             |
| `.target`  | 여러 Unit을 묶은 시스템 상태 |
| `.socket`  | 통신 소켓              |
| `.timer`   | 예약 실행              |
| `.mount`   | 파일 시스템 마운트         |
| `.path`    | 파일/디렉터리 변화 감시      |

그래서:

```
systemctl status nginx.service
```

라고 하면 systemd가 관리하는 nginx.service Unit의 상태를 확인하는 겁니다.


## 문제 6번 : 정답 3번
```
"다음 중 ( ) 안에 들어갈 내용으로 알맞은 것은?"

(ㄱ)(은)는 RAID-0의 단점인 결합 허용을 지원하지 않는 점과 RAID-1의 저장 공간의 비효율성을 보완한 레벨로 디스크의 개수를  
놀랄수록 저장공간의 효율성이 좋아진다. (ㄴ)(은)는 2개의 패리티를 사용하여 2개의 디스크 오류에도 데이터를 읽을 수 있고 최소 4개의 디스크로 구성해야 된다.

1. ㄱ RAID-1, ㄴ RAID-2
2. ㄱ RAID-3, ㄴ RAID-4
3. ㄱ RAID-5, ㄴ RAID-6
4. ㄱ RAID-7, ㄴ RAID-8
```

이번 문제는 RAID를 처음부터 전부 외우기보다 RAID 0 -> RADI 1 -> RAID 5 -> RAID 6이 각각 어떤 단점을 보안했는지 흐름으로  
보면 쉬워집니다.

먼저 RAID 자체부터 쉽게 정리하면 **여러 개의 디스크를 하나처럼 묶어서 속도, 안정성, 저장공간 효율을 높이는 기술** 이라고 보면 됩니다. 

### 1. RADI 0 - 빠르지만 하나라도 고장나면 끝

RAID 0은 데이터를 여러 디스크에 나눠서 저장합니다.  
예를 들어 
```
Disk 1 -> A, C
Disk 2 -> B. D
```
두 디스크가 동시에 일을 하기 때문에 빠릅니다.  
이것을 **Striping**이라고 합니다.

하지만 문제가 있습니다.
```
Disk 1 고장
-> A, C 사라짐
-> 원래 파일 복구 불가
```

### 2. RAID 1 - 안정하지만 저장공간 낭비

RAID 1은 똑같은 데이터를 두 디스크에 복사합니다.
```
Disk 1 -> ABCD
Disk 2 -> ABCD
```
이걸 Mirroring이라고 합니다. 

Disk 1이 죽어도
```
Disk 2 -> ABCD
```
가 남아 있으니 안전합니다.

하지만 1TB 디스크 두 개를 사용해도 실제 저장 가능한 데이터는 대략 1TB 입니다.
```
1TB + 1TB
= 물리적으로 2TB

하지만
실제 데이터 저장 공간 ≈ 1TB
```

그래서 RAID 1은 안전하지만 저장공간 효율이 나쁩니다.

### 3. 그래서 RAID 5가 등장

문제의 첫 번째 설명 RAID-0의 장애 허용 불가 문제와 RAID-1의 저장 공간 비효율성을 보안했습니다.  
이것이 **RAID-5**입니다.

RAID 5는 데이터를 나눠 저장함녀서 Parity(패리티)라는 복구용 정보도 같이 저장합니다.  
예를 들어 아주 단순하게
```
Disk 1 → 데이터 A
Disk 2 → 데이터 B
Disk 3 → 복구 정보 P
```
여기서 Disk 1이 고장 나더라도
```
B + P
↓
A를 계산해서 복구
```

즉 RAID 5는 디스크 1개가 고장 나도 데이터를 복구할 수 있습니다.

#### 패리티가 무엇인가?

잃어버린 데이터를 다시 계산하기 위한 힌트라고 보면 됩니다.

예를 들어 
```
A + B = 10
```

이라는 정보를 가지고 있는데 B가 `4`라는 걸 알고 있다면

```
A + 4 = 10
-> A = 6
```

처럼 잃어버린 값을 알아낼 수 있습니다.  
실제 RAID의 패리티 계산은 이런 단순 덧셈은 아니지만, 개념은 **나머지 데이터 + 패리티를 이용해서 고장 난 디스크의 데이터를 복원  
이라고 보면 됩니다.

#### RAID 5 저장 공간은?
디스크가 `N`개라면 대략 **사용 가능 공간 = N - 1개 디스크 분량** 입니다.  

예를 들어 1TB 디스크가 3개라면
```
3TB 물리 공간

1TB 정도 → 패리티 용도
2TB 정도 → 실제 데이터 저장
```

4개라면
```
4TB
-> 실제 약 3TB 사용
```

10개라면
```
10TB
-> 실제 약 9TB 사용
```

그래서 문제에서 **"디스크 개수를 늘릴수록 저장공간 효율성이 좋아진다."** 라고 하는 것입니다. 

### RAID 6은 RAID 5보다 더 안전
문제의 두 번째 설명 2개의 패리티를 사용하여, 2개의 디스크 오류에도 데이터를 읽을 수 있고, 최소 4개의 디스크로 구성  
이건 거의 그대로 RAID 6의 정의입니다.

RAID 5 : 패리티 1개 분량 (디스크 1개 장애까지 버팀)  
RAID 6 : 패리티 2개 분량 (디스크 2개 장애까지 버팀)

그래서 ㄴ = RAID 6 이 되는 겁니다.  
RAID 6의 실제 사용 가능 공간은 대략 N - 2 개 디스크 분량입니다.

## 문제 7번 : 정답 2번
```
"다음 중 프로세스에 대한 설명으로 틀린 것은?"

1. 실행(Executing) 중인 프로그램을 말한다.
2. TCB(Thread Control Block)를 지닌 프로그램을 말한다.
3. 사용자가 실행한 프로세스는 중간에 중지시킬 수 있다.
4. 백그라운드 프로세스와 포어그라운드 프로세스로 나눌 수 있다.
```

이번 문제는 **프로세스(Process)와 스레드(Thread)의 차이를 알고 있느냐를** 보는 문제입니다.  
핵심은 **프로세스는 PCB(Process Control Block)를 가지고 스레드는 TCB(Thread Control Block)를** 가집니다.

### 1. 실행 중인 프로그램
프로그램은 그냥 파일 상태일 수도 있습니다.

예를 들어 `/user/bin/nginx` 이 파일이 디스크에만 있으면 그냥 프로그램입니다.  
그런데 실행하면 `nginx` 메모리에 올라가서 CPU를 사용하면서 동작합니다.  

이 상태를 **프로세스 = 실행 중인 프로그램**이라고 합니다. 

### 2. TCB를 가진 프로그램

프로세스는 운영체제가 관리하기 때문에 **PCB**라는 정보를 가지고 있습니다.  
PCB에는 대략 
- 프로세스 ID
- 현재 상태
- CPU 관련 정보
- 메모리 정보
- 스케줄링 정보

같은 게 들어가게 됩니다.

즉
```
Process 
-> PCB
```

반면 스레드는
```
Thread
-> TCB
```
입니다.

### 3. 사용자가 중간에 중지 가능
예를 들어 터미널에서 어떤 프로그램이 실행 중이면 `Ctrl + C`로 중지할 수 있고,  
PID를 알고 있다면 `kill 1234` 같은 명령으로 종료할 수도 있습니다.

즉 사용자가 프로세스를 중간에 멈출 수 있으므로 맞는 설명입니다.

### 4. Foreground / Background
리눅스에서 프로세스는 실행 방식에 따라 이렇게 나뉠 수 있습니다.

#### Foreground
터미널을 자복 직접 실행되는 프로세스  
예
```
python app.py
```
이 경우 실행 중에는 터미널을 계속 점유합니다.

#### Background
뒤에서 실행되는 프로세스
예
```
python app.py &
```
뒤에 `&`를 붙이면 백그라운드 실행입니다.

## 문제 9번 : 정답 4번
```
"다음 중 리눅스에 관한 설명으로 틀린 것은?"

1. 최근 리눅스 운영체제는 SSD(Solid State Drive)를 지원한다.
2. 리눅스는 이더넷(Ethernet) 등 대부분의 네트워크 인터페이스를 지원한다.
3. 최근 64비트 리눅스 운영체제는 물리적 메모리 용량을 64TB까지 지원한다.
4. 대부분 리눅스 배포판에서는 인텔사의 x86 계열 CPU만을 기본적으로 지원한다.
```

이 문제는 **"리눅스가 어떤 하드웨어를 얼마나 폭넓게 지원하느냐"**를 보는 문제라고 이해하면 됩니다.

| 보기                          |    판단 | 핵심                         |
| --------------------------- | ----: | -------------------------- |
| 1. SSD 지원                   |     O | 최근 리눅스는 SSD 지원             |
| 2. Ethernet 등 네트워크 인터페이스 지원 |     O | 다양한 네트워크 장치 지원             |
| 3. 64비트에서 큰 물리 메모리 지원       | O로 출제 | 64비트 리눅스는 매우 큰 메모리 공간 지원   |
| 4. x86 CPU만 기본 지원           | **X** | 리눅스는 ARM 등 다양한 CPU 아키텍처 지원 |

### 1. SSD를 지원한다.

SSSD는 HDD 처럼 데이터를 저장하는 장치입니다.  
리눅스에서도 당연히 SSD를 사용할 수 있습니다.

예를 들어 서버에
```
SSD
↓
Linux
↓
ext4 / XFS 등의 파일 시스템
```
형태로 사용할 수 있습니다.

### 2. Ethernet 등 네트워크 인터페이스를 지원한다.
이것도 앞에서 봤지

리눅스는 
- Ethernet
- Wi-Fi
- PPP
- 다양한 NIC(Netwrok Interface Card)
같은 여러 네트워크 장치를 지원합니다.

### 3. 최근 64비트 리눅스 운영체제는 물리적 메모리 용량을 64TB까지 지원한다.

리눅스는 단순히 프로그램을 실행하는 껍데기가 아니라, **컴퓨터의 하드웨어 자원을 관리하는 운영체제**입니다.  
그 하드웨어 지원 중 하나가 바로 RAM(주기억장치)입니다.

즉 이런 관계입니다.
```
컴퓨터 하드웨어
├─ CPU
├─ RAM
├─ SSD/HDD
├─ 네트워크 카드
└─ 기타 장치

        ↑
        │ 관리
        │
      Linux
```
그래서 "리눅스가 SSD를 지원한다.", "리눅스가 Ethernet을 지원한다.", "리눅스가 RAM을 최대 얼마까지 지원한다."  
이런 것들이 전부 **리눅스가 어떤 하드웨어를 얼마나 지원하느냐**를 설명하는 문장이 되는 것입니다.

다시 문제 3번으로 돌아와서 **최근 64비트 리눅스 운영체제는 물리적 메모리 용량을 64TB까지 지원한다.**  
여기서 `물리적 메모리`는 그냥 **컴퓨터에 실제로 꽂혀 있는 RAM** 이라는 뜻입니다.

그래서 이 문장을 쉽게 바꾸면 **"이 리눅스 컴퓨터에 RAM을 아주 많이 꽂아도, 최대 64TB까지 인식하고 사용할 수 있다." 
즉 최대 용량이 64TB까지다 라는 설명이기 때문에 맞는 설명입니다.


### 4. 대부분의 리눅스 배포판이 Intel x86 CPU만 지원한다.

리눅스는 **x86만 지원하는 운영체제**가 아닙니다.  
대표적으로
```
x86 / x86-64
→ 일반 PC / 서버

ARM
→ Raspberry Pi / 스마트폰 / 서버

RISC-V
→ 새로운 오픈 CPU 아키텍처

PowerPC
→ 일부 서버 / 임베디드
```
등 다양한 CPU 아키텍쳐에서 동작할 수 있습니다.

## 문제 10번 : 정답 4번 
```
"다음 중 시그널(Signal)에 대한 설명 중 틀린 것은?"

1. SIGKILL은 프로세스를 강제로 종료시킨다.
2. SIGINT는 키보드로부터 오는 인터럽트 시그널로 실행을 중지시킨다.
3. SIGQUIT는 터미널에서 입력된 정지 시그널로 Ctrl + \ 입력 시 보내진다.
4. SIGSTOP은 실행 정지 후 다시 실행하기 위해 대기시키는 시그널이다.
```

이 문제는 리눅스에서 프로세스에 보내는 **시그널(Signal)** 각각의 역할을 구분하는 문제입니다.  
먼저 시그널부터 아주 쉽게 보면 **시그널 = 실행 중인 프로세스에게 운영체제나 사용자가 보내는 "명령/알림"** 이라고 보내면 됩니다.

예를 들면 프로세스에게 
```
프로세스에게

"종료해"       → SIGTERM
"당장 죽어"    → SIGKILL
"잠깐 멈춰"    → SIGSTOP
"다시 움직여"  → SIGCONT
```
이런 느낌입니다.

| 시그널       | 의미                   | 대표 입력         |
| --------- | -------------------- | ------------- |
| `SIGKILL` | 강제 종료                | `kill -9 PID` |
| `SIGINT`  | 인터럽트, 실행 중단 요청       | `Ctrl + C`    |
| `SIGQUIT` | 종료 요청 + 보통 Core Dump | `Ctrl + \`    |
| `SIGSTOP` | 프로세스 실행을 일시 정지       | 직접 signal 전달  |

### 1. SIGKILL은 프로세스를 강제로 종료
`SIGKILL`은 아주 강한 종료 신호입니다. `kill -9 1234`라고 하면 PID 1234 프로세스에 `SIGKILL`을 보냅니다. 
프로세스가 이 시그널을 무시하거나 처리해서 막을 수도 없습니다.

### 2. SIGINT는 키보드 인터럽트
터미널에서 프로그램을 실행하다가 `Ctrl + C`를 누르면 보통 `SIGINT`가 전달됩니다.  
`INT = Interrupt`라고 보면 쉽습니다.

```
Ctrl + C
   ↓
SIGINT
   ↓
"지금 실행 중인 작업을 중단해"
```

### 3. SIGOUIT는 터미널에서 입력된 "정지" 시그널
`Ctrl + \`을 누르면 SIGQUIT가 전달된다는 부분은 맞습니다. 그러나 틀린 부분은 "정지 시그널"이라고 설명한 부분입니다.  
SIGQUIT는 단순히 프로세스를 잠깐 멈춰두는 시그널이 아니라 프로세스에게 종료(Quit)를 요청하면서, 기본 동작으로 Core Dump를 남길 수 있는 시그널입니다.

```
Ctrl + \
   ↓
SIGQUIT
   ↓
프로세스 종료
+
Core Dump 생성 가능
```

그래서 `SIGQUIT = 종료(Quit) + Core Dump 로 구분하면 됩니다. 

### 4. SIGSTOP은 실행을 정지시키고 대기
이건 진짜 **"잠깐 멈춰"**에 가까운 시그널입니다.
```
프로세스 실행 중
      ↓
   SIGSTOP
      ↓
   일시 정지
      ↓
   SIGCONT
      ↓
   다시 실행
```

즉 **SIGSTOP = 프로세스를 죽이지 않고 멈춰둠** 그리고 다시 실행하면 `SIGCONT`를 보낼 수 있습니다.

## 문제 12번 : 정답 2번
```
"다음 중 아래의 파일을 실행하는 방법으로 틀린 것은?"

[root@ihd ~] #
[root@ihd ~] ls -l script.sh
[root@ihd ~] -rw-r--r-- 1 root root 21 Feb 18 17:28 script.sh
[root@ihd ~] #
[root@ihd ~] #

1. #sh script.sh
2. # ./script.sh
3. #. script.sh
4. #srouce script.sh
```

이 문제에서 2번 `./script.sh`가 틀린 이유는 `script.sh` 파일에 실행 권한 (`x`)가 없기 때문입니다. 

핵심은 `ls -l scrip.sh`의 권한 부분을 보는 문제입니다.  
`x`는 execute = 실행 권한입니다. 그래서 파일 상태가 
```
r → 읽기 가능
w → 쓰기 가능
x → 실행 가능
```
인데 현재 `script,sh`는 실행 권한이 없는 겁니다.

### 1. `sh script.sh` -> 가능
```
sh script.sh
```

이건 `script.sh` 자체를 직접 실행하는게 아닙니다.  
`sh` 라는 프로그램을 실행하고, `script.sh` 파일을 읽어서 실행해 달라는 뜻입니다.

구조는 
```
sh 실행
  ↓
script.sh를 읽음
  ↓
내용 실행
```

그래서 `script.sh`에 `x` 권한이 없어도 읽기 권한만 있으면 실행 가능합니다.

### 2. `./script.sh` -> 불가능

이건 의미가 다릅니다. `./script.sh`는 현재 디렉터리(`./`)에 있는 `script.sh` 파일 자체를 직접 실행하라는 뜻입니다.

즉 운영체제가 파일을 직접 실행하려고 하니깐 실행 권한 `x`가 반드시 필요합니다.

현재 
```
-rw-r--r--
```
라면 `x`가 없으니깐 `./script.sh`를 하면 보통 `Permission denied`가 나와 만약 먼저 `chmod +x script.sh` 해서 `-rwxr-xr-x` 처럼 `x` 권한을 추가하면 그때는 `./script.sh`를 실행할 수 있습니다.

### 3. `. script.sh` -> 가능
```
. script.sh
```

여기서 `.` `source` 명령어의 축약형입니다.  
즉 현재 셀이 script.sh 내용을 읽어서 실행하라 뜻입니다.

파일 자체를 직접 실행하는 게 아니기 때문에 `x` 권한이 필요하지 않습니다.
```
현재 Bash
   ↓
script.sh 읽음
   ↓
현재 Bash에서 실행
```

### 4. `source script.sh` -> 가능

source도 3번의 `.`과 같은 역할입니다.


## 문제 13번 : 정답 4번
```
"현재 터미널에서 아파치 웹 서버 데몬(httpd)을 실행하기 위한 명령으로 틀린 것은?"

1. /etc/rc.d/init.d/httpd start
2. service httpd start
3. /etc/init.d/httpd start
4. ntsysv httpd on
```

이번 문제는 **"지금 당장 httpd를 실행하는 방법"과 "부팅할 때 자동으로 실행되도록 설정하는 방법"을 구분할 수 있느냐**를 구분하는 문제입니다.

| 보기                             | 역할                    | 지금 httpd 실행? |
| ------------------------------ | --------------------- | -----------: |
| `/etc/rc.d/init.d/httpd start` | httpd 시작 스크립트를 직접 실행  |            O |
| `service httpd start`          | service 명령으로 httpd 시작 |            O |
| `/etc/init.d/httpd start`      | httpd 시작 스크립트를 직접 실행  |            O |
| `ntsysv httpd on`              | 서비스 자동 시작 여부 설정 쪽     |        **X** |

### 먼저 `httpd`가 무엇인가?
`httpd`는 Apache 웹 서버의 **데몬(백그라운드 서비스)** 이름입니다.

즉 Apache 웹 서버 -> httpd 데몬  
웹 요청을 계속 기다리면서 뒤에서 실행되는 프로그램이라고 보면 됩니다.

### 1. `/etc/rc.d/init.d/httpd start`
예전 SysV init 방식에서는 서비스마다 실행 스크립트가 있었습니다.  
`etc/rc.d/init.d/httpd` 이 파일에게 start를 전달하면 "httpd 서비스를 지금 시작해"라는 뜻입니다.

그래서 `etc/rc.d/init.d/httpd start` -> 현재 httpd 실행 O

### 2. `service httpd start` 
이것도 같은 목적입니다.

`service httpd start`를 자연어로 읽으면 `httpd` 서비스를 `start` 해라  

즉
```
service
   ↓
httpd의 init 스크립트 실행
   ↓
Apache 시작
```

### 3. `/etc/init.d/httpd start`
이것도 1번과 거의 같은 방식입니다.

예전 Red Hat 계열에서는 `/etc/init.d` 가 `/etc/rc.d/init.d`와 연결되어 있거나 같은 init 스크립트들을 가리키는 형태로 사용됐습니다.

그래서 `/etc/init.d/httpd start` 역시 httpd를 지금 시작하는 명령입니다.

### 4. `ntsysv httpd on` 
`ntsysv`는 앞에서 배운 것처럼 **서비스를 지금 실행하는 도구가 아닙니다**  
주 역할은 **부팅하거나 특정 Runlevel에 들어갈 때 어떤 서비스를 자동 실행할지 설정** 하는 것입니다. 

대략 이런 화면을 띄워서:
```
[*] sshd
[*] crond
[ ] httpd
[ ] vsftpd
```

`httpd`를 체크하면 "다음부터 이 서비스를 자동으로 시작하도록 설정해" 라는 의미입니다.
즉 
```
service httpd start
→ 지금 켜!

ntsysv
→ 나중에 부팅할 때 자동으로 켤지 설정!
```
이 차이가 핵심입니다. 

그리고 `ntsysv`는 원래 **TUI 체크박스 방식으로 설정하는 프로그램**이라 `ntsysv httpd on` 이라는 표현 자체도 일반적인 사용법과 맞지 않습니다.

a.txt b.txt c.txt d.txt

1. [bd]

a.txt
b.txt
c.txt
d.txt

```
b.txt
c.txt
d.txt
```

즉 [b-d] -> b 또는 c 또는 d 그래서 명령어 실제로는 이런 형태라고 보면 됩니다.

a.txt → a는 b~d 범위가 아님 → X
b.txt → O
c.txt → O
d.txt → O
```

따라서 
```
b.txt
c.txt
d.txt
```
가 출력되는 것입니다. 

| 표현       | 뜻                        | 결과                        |
| -------- | ------------------------ | ------------------------- |
| `[bd]`   | b 또는 d                   | `b.txt`, `d.txt`          |
| `[!bcd]` | b,c,d가 **아닌** 문자         | `a.txt`                   |
| `[b-d]`  | b부터 d까지                  | `b.txt`, `c.txt`, `d.txt` |
| `[b~d]`  | b, `~`, d 중 하나로 해석될 수 있음 | 원하는 범위 표현 아님              |

특히 `[ ]` 안에서 `-`가 중요합니다.
```
[a-c] → a, b, c
[0-3] → 0, 1, 2, 3
[b-d] → b, c, d
```

그리고 `!`는 `[ ]` 맨 앞에서 **제외**라는 뜻입니다. 

## 문제 15번 : 정답 3번
```
"다음 중 저널링(Jornaling)기술의 특징으로 틀린 것은?"

1. 데이터를 디스크에 쓰기 전에 별도의 로그에 데이터를 남겨 놓는 기술입니다.
2. 저널링 기술이 적용된 파일 시스템은 ext3, JFS, ReiserFS 등이 있다.
3. 전원 공그 문제나 시스템 오류와 같은 상황에 복구가 불가능하다.
4. fsck로 복구하는 것보다 속도가 빠르고, 복구의 안정성도 뛰어나다.
```

이번 문제는 저널링이 **"갑자기 전원이 꺼지거나 시스템이 죽었을 떄 파일 시스템을 빨리 복구하기 위한 기술"**이라는 점만 잡으면 풀 수 있습니다.

쉽게 정리하자면 저널링은 **디스크에 실제 변경을 반영하기 전에, "내가 지금 이런 변경을 할 거야"라는 기록을 먼저 남겨두는 방식** 입니다.

예를 들어 파일을 수정한다고 해보겠습니다.
```
1. "A 파일을 이렇게 바꿀 예정" -> 저널에 기록
2. 실제 디스크에 변경
3. 작업 완료
```

그런데 2번 도중 갑자기 전원이 꺼졌다고 해보겠습니다.

```
저널 기록은 남아 있음
↓
부팅 후
↓
"아, 이 작업 하다가 죽었구나"
↓
저널을 보고 복구
```

그래서 저널링의 목적 자체가 **장애 상황에서 복구를 쉽게 만드는 것**입니다.

### 1번
데이터를 디스크에 쓰기 전에 별도의 로그에 데이터를 남긴다.

시험에서는 맞는 설명으로 보면 됩니다.  
정확히는 저널링 파일 시스템이 변경 작업에 대한 정보를 저널에 기록해두는 것입니다.

즉
```
"무슨 변경을 할 건지 먼저 기록"
↓
실제 파일 시스템 변경
```

### 2번
`ext3`, `JFS`, `ReiserFS`는 대표적인 저널링 파일 시스템입니다.  
추가로 `ext4`, `XFS`도 저널링을 사용합니다. 

시험에서는 
```
ext2 → 저널링 X
ext3 → 저널링 O
ext4 → 저널링 O
```
이렇게 기억하면 좋습니다.

### 3번 <- 틀린 보기
전우너 공급 문제나 시스템 오류 같은 상황에 복구가 불가능하다.  
이것은 저널링의 목적과 정반대입니다.

저널링은 오히려 **전원 장애나 시스템 크래시가 났을 떄 복구하기 쉽게 하려고 만든 기술** 입니다.  
그래서 
```
전원 꺼짐
시스템 오류
비정상 종료
↓
저널 확인
↓
파일 시스템 상태 복구
```
가 가능합니다.

물론 저널링이 있다고 해서 **모든 데이터 손실을 100% 막는 것**은 아닙니다.  
하지만 파일 시스템의 일관성을 훨씬 빠르고 안정적으로 복구하는 데 도움이 됩니다. 

### 4번
`fsck`는 파일 시스템을 검사하고 복구하는 명령입니다.

저널링이 없으면 비정상 종료 후
```
디스크 전체를 검사
↓
어디가 잘못됐는지 찾음
↓
복구
```
해야 할 수 있습니다.

반면 저널링이 있으면 
```
저널만 확인
↓
중간에 끊긴 작업 확인
↓
복구
```
가 가능하니깐 일반적으로 훨씬 빠른 겁니다.

```
"다음 중 LVM의 구성 요소에 대한 설명으로 틀린 것은?"

1. VG(Volume Group) : PV들의 집합 (Group) 이며 LV를 할당할 수 있음
2. PE(Physical Extent) : 실제 디스크에 물리적으로 분할한 파티션, /dev/sdbl/dev/sdcl 등이 이에 해당
3. PV(Physical Volume) : 블록 장치 전체 혹은 파티션들은 LVM에서 사용할 수 있도록 변환한 것을 의미
4. LV(Logical Volume) : VG에서 사용자가 필요한 만큼 할당하여 만들어지는 공간, 물리적 디스크에서 분할하여 사용하는 파티션
```

이번 문제는 LVM을 먼저 **"여러 디스크 공간을 한 덩어리로 모은 다음, 필요한 만큼 다시 나눠 쓰는 기술"** 이라고 이해하면 쉽습니다.

PV = 실제 디스크/파티션을 LVM용으로 만든 것
VG = PV들을 합친 큰 저장공간
LV = VG에서 필요한 만큼 떼어낸 논리 공간
PE = PV를 잘게 나눈 작은 물리 단위


## 문제 17번 : 정답 4번
```
"다음 중 셸(Shell)의 특징으로 틀린 것은?"

1. bash(베시셸)는 Tab를 이용한 자동완성 기능을 제공한다.
2. 사용자의 로그인 셸 정보는 /etc/passwd 파일의 7번째 필드에 기록되어 있다.
3. ksh은 history 명령어를 이용하여 최근 사용한 명령어를 검색하고, 'r [옵션]' 형식으로 재실행할 수 있다.
4. 리눅스에서는 sh(본셸)를 기본으로 bash(배시셸)와 csh(C셸) 계열의 장점만 결합한 ksh(콘셸)을 표준으로 하고 있다.
```

이 문제는 셸 종류별 특징과, **리눅스에서 어떤 셸이 일반적으로 기본 셸로 사용되는지**를 묻는 문제입니다.

먼저 셸은 아주 쉽게 말하면 **사용자가 입력한 명령어를 받아서 리눅스 커널에게 전달해주는 명령어 해석기**입니다. 

```
사용자
  ↓
Shell
  ↓
Linux Kernel
  ↓
하드웨어
```

예를 들어 터미널에서 `ls`를 입력하면 셸이 `ls` 명령을 해석해서 실행해주는 것입니다.

| 보기                      | 판단    | 핵심                    |
| ----------------------- | ----- | --------------------- |
| 1. bash의 Tab 자동완성       | O     | Bash의 대표 기능           |
| 2. `/etc/passwd` 7번째 필드 | O     | 로그인 셸 정보              |
| 3. ksh의 history와 `r`    | O     | 명령 기록·재실행 기능          |
| 4. Linux의 표준 셸이 ksh     | **X** | 일반적으로 Bash 계열이 널리 사용됨 |
